# ADR-005 — Office subscriptions on Stripe: the provider is the source of truth

**Status:** Accepted
**Date:** 2026-11-17
**Related:** SPEC-012 (BR-012-06, BR-012-08, BR-012-09, BR-012-13, BR-012-14, BR-012-21, BR-012-28), SPEC-002 (`OFFICE_PLAN_SOURCE`), SPEC-011, AR-10, AR-15, AR-17, AR-20, AR-24, SC-11, #12

## Context

SPEC-012 puts an advisor plan on an **office** and requires that state changes come only from the payment provider and are idempotent and order-independent: delivering one event twice changes nothing the second time, and the stored state ends equal to the provider's current state whatever order the events arrived in (BR-012-13). The code before it applied each Stripe event's payload to the **user**, in arrival order, with no event de-duplication.

Stripe delivers at least once, with no ordering guarantee, and retries on any non-2xx. So the handler meets: the same event twice (also concurrently), `customer.subscription.deleted` before the earlier `updated`, `invoice.paid` before `checkout.session.completed`, and a process that dies between two writes. Two further facts shape the design: there is no MongoDB replica set in the Compose and local environments (no transactions, AR-15), and the office does not exist until the first payment is confirmed, while SPEC-011, which owns offices, is not built yet.

## Options

1. **Apply each event's payload, in arrival order, with an event-id check.** Simple. It is wrong whenever order matters: a stale `updated` processed after `deleted` revives a lapsed office. De-duplicating by id does not help, the two events have different ids.
2. **Order events by their creation time and ignore older ones.** Stripe documents that `created` is not a reliable order and a retried event keeps its old time; clocks and retries make "older" a guess, and one lost event leaves the record wrong forever.
3. **Treat the event as a pointer and re-read the provider (chosen).** On any subscription-related event, retrieve the subscription from Stripe and store what it says now. A late, duplicated or reordered event then writes the same thing as the right one. Left alone, two concurrent syncs can still race: sync A reads, the provider changes, sync B reads and writes, then A writes its older read.
4. **Option 3 plus a per-record lease around read-and-write (chosen).** The record carries `syncLeaseToken` / `syncLeaseUntil`. A sync takes the lease with one conditional update, retrieves **inside** it, and writes conditional on the token, releasing it in the same write. Syncs of one subscription are strictly ordered, so each read is newer than the write before it. A loser that merely answered `WEBHOOK_BUSY` (503) would turn every burst into delayed retries, so the lease is combined with a re-sync request (see Decision).
5. **A job that reconciles all subscriptions periodically.** A safety net, not a replacement: it leaves a window of wrong state after every event. Not needed to meet BR-012-13, and it can be added later on top of the same sync.

For the office, which does not exist at checkout:

- **A. Create the office at checkout.** An abandoned checkout would leave an office, and a payment the platform never confirmed would own one. Contradicts BR-012-07/BR-012-09.
- **B. Create it on the first confirmed payment through a port (chosen).** `OFFICE_PROVISIONER`, bound by SPEC-011, must be idempotent by `subscriptionRef` (its unique index), because two deliveries can race; our attach is a conditional update. Until SPEC-011 binds it, the default fails closed and the billing PR refuses a checkout that could not get its office.

## Decision

- **Stripe is the source of truth for a subscription; we store a synchronised copy.** The webhook verifies the signature over the raw body (only a signature failure is a 400; a failure to map a verified event is a 5xx fault), records the event by its id (`paymentEvents`, unique), and **never reads state from the payload**: it resolves our record (provider id, else the ref in the event, else the ref the provider's subscription carries), takes the lease, retrieves inside it, maps the snapshot with a pure function (`subscriptions/domain/provider-state.ts`) and writes conditional on the lease. A subscription that carries our ref but has no record, a ref that does not match its record, or a first activation on a price no plan maps to is a fault (5xx, retried and reported), never an acknowledgement; only a subscription with **no** ref is legacy and ignored.
- **Bursts are coalesced, not refused.** A delivery that cannot take the lease does ONE conditional update that matches only while a lease is live (`syncRequestedAt`) and is done: the holder's write reads that mark atomically with the release (the update returns the document as it was) and, if it is set, reads the provider again, at most three times, then answers `WEBHOOK_BUSY`. A mark that arrives after the release matches nothing, so its sender takes the lease itself (three attempts, then `WEBHOOK_BUSY`). So every read that follows an event happens after it, and a burst never becomes a delayed 503. The exception is the payment-failed event, which needs its own read to decide the email: when only covered, it is answered `WEBHOOK_BUSY` and the retry sends it.
- **Idempotency by event id with reprocessing of the unprocessed.** A repeat of a processed event is a no-op; a repeat of one never marked processed (`processedAt` is set only after full handling) is handled again, which is safe because the sync is idempotent.
- **One in effect per office is enforced by the database and decided by the provider.** A partial unique index on `officeId` where the office exists and the status is `ACTIVE`, `PAST_DUE` or `CANCELING` refuses a second one. The index only says they collide, so the service first reads the conflicting subscription again from the provider under its own lease: if it is no longer in effect it lapses and the incoming one is written. If both are in effect at the provider, the one with the **later first payment** (else the later creation) is cancelled at the provider (an idempotent cancel) and synced to `LAPSED`, whichever lost the index race, so a late reactivation never takes the office from the subscription that has been paid longest; the warning names ids only.
- **The plan the access context reads is computed on read**: `SubscriptionOfficePlanSource` is bound to `OFFICE_PLAN_SOURCE` in `AccessModule` only (BR-002-21) and derives `advisorPlanActive` and `readOnly` on every request from the stored `lapsedAt`, the injected clock and `SUBSCRIPTION_GRACE_DAYS`, in a pure `domain/` (100% branch). **The end of the grace period needs no job.** The `status` itself, though, changes only by events or by a read of the provider, so a lost event leaves a record stale until the next one: a reconcile job that re-reads every non-lapsed subscription is part of the billing PR (same issue, #12).
- **Ports for what other specs own** (`OFFICE_PROVISIONER`, `OFFICE_MEMBERS_SOURCE`, `PAYMENT_FAILED_NOTIFIER`), each with a fail-closed default, bound in `SubscriptionsModule` when their spec lands. The provisioner must be idempotent by `subscriptionRef` **and** return the buyer's existing office for another ref of the same buyer; the service logs a warning when the office kept differs from the one returned. The payment-failed email is **claimed** on the event before it is sent, so a replay sends it once.
- **Our vocabulary at the port** (AR-10, AR-20): `PaymentGateway` takes and returns `Date` and `Decimal` reais and provider ids; only the Stripe adapter imports `stripe`, and the Stripe API's period-on-item and invoice-parent shapes stay inside it. The adapter refuses a subscription that does not have exactly one item, ignores an event of the other mode than the key (test vs live) as `unhandled`, and gives its client an 8 s timeout and 2 retries, so a read ends (24 s worst case) before the 30 s lease can be taken over.
- **Plan prices are not changed in place.** A plan's provider price id never changes (subscribers keep paying it, BR-012-04); `plans:upsert` refuses a changed price id and a price id that is another plan's. A new price is a new code, and the old one is withdrawn.

## Consequences

- **After each sync our record equals what the provider said at that read, and a burst is coalesced into reads that all follow the last event**, without a transaction or a replica set. The cost is one extra Stripe API read per subscription event (and one more when a burst marks the holder), and a short window in which a record is behind the provider. Events lost for good (Stripe gives up after about 3 days of retries; a holder that dies after acknowledging a covered event) leave a record stale until the next event, which the billing PR's reconcile job heals.
- **A confirmed payment never sits unprocessed silently**: any fault (Stripe unreachable, no office store yet) answers 5xx, leaves the event unprocessed and is retried by Stripe for about 3 days.
- **Webhook latency depends on Stripe's API.** A slow retrieve holds the lease up to 30 s (the client gives up first); after that another sync may take it, and the first, if it ever writes, finds its token gone and writes nothing.
- **Duplicate payments are cancelled, not refunded, by the code.** The warning is the operator's signal to refund by hand; automating it belongs with the refund flow of the billing PR.
- **`pending_if_incomplete` upgrades take effect when the provider bills the new price**, which is when the proration is paid; the sync follows the price it reads (BR-012-16).
- **The email claim is a 10-minute lease.** A crash between the claim and the send loses the claim at its end and the retried event sends the email; a failed send, or nobody to tell, releases the claim at once; once somebody was told it is never sent again for that event.
- **One office per subscription ref is guaranteed here; one office per buyer is not.** It needs the provisioner contract above and the billing PR's **one pending checkout per buyer** guard. Until the billing PR, no checkout exists, so none can race.
- **Provider settings are part of the design** (listed in ARCHITECTURE §13): dunning must end in cancelling the subscription, the portal must be restricted, the seven events must be enabled.
- **Forecloses** trusting any payload field for state, and per-user subscriptions (`users.role`, `subscriptionStatus` and the Stripe ids are no longer written; their removal is an expand/contract follow-up, AR-28).
- **Reopen if** the platform gets a replica set and a need for multi-document guarantees that the lease cannot give, or if Stripe stops allowing a retrieve inside the webhook's time budget.

## Update — the billing PR (2026-11-18)

The first PR built the sync; this one builds what an office does with it (checkout, change, cancel, refund, portal), the journey slots, the payment-failed email and the safety net the Consequences above promised. Nothing above changes: the provider is still the only source of state, and every action below asks the provider and then reads it back through the same lease-and-dirty-mark sync (`SubscriptionsService.refresh`). Rules: SPEC-012 BR-012-06..BR-012-11, BR-012-16..BR-012-20, BR-012-22..BR-012-25, BR-012-29, SC-11, AR-13, AR-14, AR-15.

### Decisions

- **No endpoint writes state; upgrades follow the paid price.** An upgrade asks the provider for the prorated difference (`proration_behavior: always_invoice`) with `payment_behavior: pending_if_incomplete`, which changes the subscription's price only once that invoice is paid. Our record, limit included, changes when the sync reads the new price (BR-012-16); an unpaid upgrade changes nothing. A downgrade (equal or lower limit) is a subscription schedule: the current price to the period end, then the new one (`end_behavior: release`), read back as the scheduled change (BR-012-17). The comparison is on the subscription's own copy of its limit, so a catalog edit never turns an upgrade into a downgrade (BR-012-04). A pending schedule is released before an upgrade and before a cancel (it would fight the change).
- **One open checkout per office, or per buyer while there is no office, held by the database.** Options: (a) check then insert — two requests at once both pass; (b) a lock document — one more collection to keep; (c) a unique key on the record (**chosen**): `openCheckoutKey` (`office:<id>` / `buyer:<id>`) on the PENDING record, unique among the records that carry it (a partial index, MongoDB cannot filter on a missing field), removed by the sync as soon as the provider moves the subscription out of PENDING. An earlier attempt is replaced only when nothing was paid: its session is expired at the provider (a session already paid refuses the new checkout, `CHECKOUT_IN_PROGRESS`), a record with no session after 2 minutes is an orphan of a crashed creation and is removed, and anything the provider already made a subscription of is never replaced. It keeps one office per buyer together with the provisioner contract.
- **"A full refund of what it paid" means every payment of the first subscription, and is claimed, keyed per invoice and repaired by retry, without a transaction.** Eligibility is pure and half-open (`now < firstPaidAt + REFUND_WINDOW_DAYS`, the first PAID subscription of the office, `refundedAt` unset), judged at the instant the member's cancel was FIRST accepted (`refundRequestedAt`, the `$min` of the first claim) and BEFORE "already cancelling", so a retry after the window of a request made inside it completes, and renewal stopped on day 2 does not forfeit the right on day 5. A first subscription that charged nothing (a 100% coupon, `firstPaymentFree`) is not an "earlier paid" one. The first payment is the invoice that CREATED the subscription (`billing_reason: subscription_create`), never `latest_invoice`: after an upgrade that is the proration alone. Cancelling then (1) claims the refund with one conditional update on `refundClaimedAt` (only for a record in effect; a claim not followed by a refund within 5 minutes can be retaken; a member who finds a LIVE claim gets `CANCEL_IN_PROGRESS`, 409, never a silent success), (2) reads every invoice of the subscription with what each paid and already refunded, voids the unpaid ones (so a proration cannot be paid after the end) and refunds each paid one what remains, with its own key `refund:<ref>:<invoiceId>` (an upgrade proration paid inside the window is refunded with the first payment; D-48's "no refund of upgrades" is read as "no refund AFTER the window"), (3) records `refundedAt`, (4) cancels at once (idempotent), (5) syncs (LAPSED, the grace period starts). A refund that returns less than the invoice paid, or that the provider cannot confirm, throws before anything is recorded or cancelled, and ANY failure before the refund is confirmed (the record of it included) gives the claim back; an idempotency or already-refunded error counts as done only after the provider's own refunded amount for that invoice is read back and covers it. A crash after (2) is repaired by the next cancel, which finds each invoice refunded in the provider's own figures and only records and ends it; a crash after (3) by the next cancel too, and in both cases by the daily reconcile job, which finishes every subscription in effect with a refund requested or made. Two members at once refund once. Options rejected: a MongoDB transaction (no replica set locally, AR-15) and refunding first with no claim (two members, two refund requests, and relying on the provider's 24 h key retention alone).
- **The same event twice at the same moment runs once.** The ledger document gets a processing claim (token and expiry, one conditional update); the losing delivery answers `WEBHOOK_BUSY` and its retry finds the event processed. A failed delivery releases its claim, a dead holder loses it at expiry. This closes the window `processedAt` alone left (two deliveries both seeing "not processed").
- **The reconcile job is the safety net, and dunning must end in cancel.** Once a day, under a run-level lock (a claim on a ledger document, so two replicas do not both run it), it (1) finishes refunds left half done, (2) asks the provider about every checkout that has a session and no subscription of ours after 10 minutes: a session the buyer PAID is read through the normal sync (`SubscriptionsService.recoverCheckout`: the office is created, a duplicate is resolved), an expired one is removed, one still open after 24 h is closed first, and a record whose session is not CONFIRMED expired is never removed (a provider error keeps it; the success page does the same lazily for its own checkout), (3) re-reads every non-lapsed record (and the ones lapsed in the last 14 days) last synced more than 12 hours ago, oldest first and bounded, a record it cannot read sorting after the others so it cannot starve the batch, and (4) removes only the checkouts whose creation never finished (no session id) after 3 days. It logs counts and records each run. It heals what Stripe stopped retrying, what a dead lease holder left unread and a payment whose events never arrived, but it cannot invent a cancellation the provider never makes, hence the required provider settings.
- **The catalog is checked against the provider before it is written.** `plans:upsert` refuses a price that does not exist, is archived (for an offered plan), or differs in amount, interval or currency, and writes the changed plans as one `bulkWrite`. MongoDB without a replica set has no multi-document transaction, so a crash inside that one command can leave a prefix; every write is an idempotent upsert and the operator re-runs the same file. True all-or-nothing needs a transaction we do not have locally.
- **Billing lives in its own module.** `SubscriptionsBillingModule` carries the controllers, the billing service and the job; `SubscriptionsModule`, which `AccessModule` imports (and `npm run grant-admin` therefore loads), keeps the sync, the plan source, the ports, the email notifier binding and `JourneySlotsService` (exported for SPEC-016). The grant script then needs no HTTP, no scheduler and no coupon catalog.

### Consequences

- The plan page itself reads no invoice: the billing history is its own route (`GET /api/office/subscription/invoices`, six a page, cut from one cached read of the newest 100 invoices), so a provider that cannot be read breaks only the history (`BILLING_HISTORY_UNAVAILABLE`), never the plan. The amount an upgrade charges now is the provider's own upcoming-invoice figure (`change-preview`), never computed here.
- After an upgrade the answer may still show the old plan: the price changes when the proration is paid, and the page shows the new one on its next read. The interface must say "awaiting payment confirmation" rather than infer it from the request.
- The buyer's open-checkout key lives until the office is ATTACHED (or the subscription lapses), not until the payment: a first subscription that the provider activated but whose office SPEC-011 could not yet create keeps blocking a second checkout of the same buyer (`SUBSCRIPTION_ALREADY_ACTIVE`). The guard is asked again after the record exists, so a payment confirmed between the check and the insert deletes the new record instead of starting a second checkout. The provisioner contract (return the buyer's existing office for another ref) remains the last line.
- A cancel that finds the refund recorded repeats the idempotent provider cancel, so two members cancelling at once may issue it twice (one refund, one end); a member who finds a live claim is told `CANCEL_IN_PROGRESS`.
- A plan change is rejected with `CHANGE_PLAN_FAILED` when the provider refuses it (an interval change with `pending_if_incomplete` is the case to verify in Stripe test mode); the price is changed first and a scheduled downgrade is released only after that succeeded. Whether Stripe accepts a price change on a subscription that still has a schedule attached is to be verified in test mode too; if it does not, the change fails safe (`CHANGE_PLAN_FAILED`) and the member releases the schedule first.
- Idempotency keys of upgrades and downgrades come from the facts of the action (subscription, current and target plan, period start, scheduled plan); the provider keeps a key 24 hours, so the same upgrade asked a third time within a day, after being undone, would be answered from its first response. Cancel and undo keys add the minute.
- The billing portal fails closed in production without `STRIPE_BILLING_PORTAL_CONFIGURATION_ID` (`BILLING_PORTAL_FAILED`): setting it is a required owner action, not a deploy blocker.
- The refund is what the provider shows the subscription was PAID, invoice by invoice, minus what was already refunded: the first payment and any upgrade proration paid inside the window. A refund made by hand in the dashboard first is not given twice.
- A member removed by SPEC-011 loses access on the next request (the context is rebuilt every time), but a checkout session they already opened can still be paid; it belongs to the office or buyer it was created for.
- **Reopen if** the platform gets a replica set (the refund claim and the catalog write can become transactions) or if Stripe offers a way to hold a subscription's items while a schedule exists, which would remove the release-before-upgrade step.
