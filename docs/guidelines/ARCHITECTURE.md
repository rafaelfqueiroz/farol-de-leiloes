## 2. Runtime topology

```
Browser ──► Next.js (frontend/, :3001)
              ├─ Server components / route handlers ──► NestJS API (backend/, :3000) ──► MongoDB
              └─ /api/* proxy routes ─────────────────┘        │
                                                               ├─► Stripe, OpenAI, SMTP, SMS/WhatsApp
                                                               ├─► Cloudflare R2 (presigned URLs)
                                                               └─► Caixa (daily list + detail pages)
Scheduled jobs (@nestjs/schedule, in the backend process):
  Caixa import (SPEC-004) · detail-page enrichment · reminders · digests · Radar · retention purge
```

|           |                                                                                                                                                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AR-01** | The browser talks only to Next.js. The backend URL and every secret stay server-side; the frontend reaches the API through server components, route handlers and `/api/*` proxy routes.                                                             |
| **AR-02** | The backend is the only process that touches MongoDB, R2 and third-party APIs. Next.js never opens a database connection.                                                                                                                           |
| **AR-03** | Every scheduled job is idempotent and safe to re-run after a crash halfway through. Each run is recorded (start, end, outcome, counts) — the Import Run of SPEC-004 BR-004-27 is the model.                                                         |
| **AR-04** | Every job has an `*_ENABLED` flag, off in tests: a spec that boots a Nest module containing a job sets its flag to `false` (or leaves the job's module out of the testing module). A job that cannot be switched off cannot be tested in isolation. |

## 3. Layering — a pure domain inside each module

Each backend module is a domain concept (`journeys/`, `offices/`, `viability/`), not a technical layer. Inside it:

```
backend/src/<module>/
  domain/            pure rules and calculations — no framework, no I/O
  <module>.service.ts         orchestrates: loads, calls domain, saves
  <module>.repository.ts      the only file that touches the Mongoose model
  <module>.controller.ts      HTTP edge: DTOs, guards, OpenAPI decorators
  schemas/           Mongoose schemas
  dto/               request/response DTOs
```

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AR-05** | **`domain/` imports no framework.** No `@nestjs/*`, no `mongoose`, no `fs`, no HTTP client, no `process.env`, no `Date.now()`. It receives everything it needs as arguments, including the current time (AR-17). Enforced by an ESLint `no-restricted-imports` rule on `**/domain/**`.                                                                                                                                            |
| **AR-06** | Business rules and calculations live in `domain/`: the viability calculator (SPEC-014), match score and Radar (SPEC-013), plan entitlements and limits (SPEC-012), phase-transition rules and phase averages (SPEC-016, SPEC-019), cost and contribution settlement (SPEC-018), holdings totals (SPEC-022), the CSV parser and change detection (SPEC-004). These are the **critical modules** with the 100% branch gate (TS-24). |
| **AR-07** | Controllers hold no logic beyond mapping a request to a service call. A controller method longer than about 15 lines is a service method waiting to be extracted.                                                                                                                                                                                                                                                                 |
| **AR-08** | Services never call `Model.find*` directly. Data access goes through the module's repository, which is where ownership scoping lives (AR-12).                                                                                                                                                                                                                                                                                     |
| **AR-09** | Modules talk to each other through exported services, never by importing another module's repository, schema or model. A module that needs another's data asks its service.                                                                                                                                                                                                                                                       |
| **AR-10** | Each external system sits behind a port named for the role, not the vendor: `PaymentGateway` (Stripe), `LanguageModel` (OpenAI), `FileStore` (R2), `Mailer` (SMTP), `CaixaSource`. The adapter takes the vendor name. Tests use hand-written fakes of the port (TS-03).                                                                                                                                                           |

The `common/` module follows AR-09 too; it is not exempted as a shared kernel. Job persistence stays behind `JobExecutionService`; callers import its framework-free run enums and record/outcome contracts from `common/job-execution.ts`. Auth consumes the `users/user-account.ts` contract through `UsersService`, and reminders resolve both auction codes and document ids through `AuctionsService` (#51, DV-09). Public contracts contain no schema or repository imports. Job execution results and auth profiles are detached plain values, including profile arrays and address objects; callers cannot save or mutate their source documents through them. `UserAddress` is shared by the account, schema and profile contracts.

The AR-09 import lint is complemented by `test/structural/module-model-boundary.spec.ts`: it rejects production `db.model(...)` and `connection.model(...)` calls, including static bracket access and optional chaining. Owning modules use their injected models; other modules ask an exported service. Test files are excluded from the production scan so their harnesses can register models.

## 4. Ownership and isolation

SPEC-002 is the source of truth. The architectural consequences:

|           |                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AR-11** | Every client-data collection carries `ownerType` (`'office' \| 'self_advised'`) and `ownerId` (SPEC-002 BR-002-01), required, set once at creation, never updated. Every compound index on it starts with `{ ownerType: 1, ownerId: 1 }`.                                                                                                                                                                      |
| **AR-12** | **Every read and write of an owned collection goes through a repository extending `OwnerScopedRepository`** (`backend/src/access/`), which merges the owner filter derived from the request's `AccessContext`. No method accepts an owner from the caller. Unscoped access (cross-owner jobs, admin under a support grant) uses separately named methods (`findAcrossOwnersForJob`) that are reviewed as such. |
| **AR-13** | `AccessContext` is built on the server from the authenticated account's **current** memberships and links on every request (BR-002-11, BR-002-15) — never from an id in the path, query or body, and never cached across requests.                                                                                                                                                                             |
| **AR-14** | A record the caller may not access returns the same `404` as a missing one (BR-002-12). Services raise `NotFound`, never `Forbidden`, for owned records.                                                                                                                                                                                                                                                       |
| **AR-15** | Plan-limit checks and the write they guard happen atomically — a conditional update or a transaction — so concurrent requests cannot exceed the limit (BR-002-13).                                                                                                                                                                                                                                             |
| **AR-16** | A collection is owned exactly when its schema has an `ownerId` path. The isolation suite enumerates the registered Mongoose models and fails on any model with `ownerId` and no isolation spec, and on any model without it that is not explicitly marked public (TS-14).                                                                                                                                      |

**The access context (SPEC-002 part 1, #2).** `backend/src/access/` (`AccessModule`, global) builds an `AccessContext` for every authenticated request. It is registered as a second global guard, `AccessContextGuard`, in `AuthModule`'s `providers` immediately after `JwtAuthGuard`: the global guards of one module run in the order they are listed, so the context is built from the user `JwtStrategy` has just read from the database (`jwt-auth.guard.spec.ts` holds the order). A public route gets none (see the @Public rule below). The context lives on the request under a symbol and a handler reads it with `@Access()`, which refuses a request without one (`UNAUTHENTICATED`) rather than inventing it. It is frozen and only `AccessContextFactory` can construct it (its constructor demands a token private to `access-context.ts`), so no controller can hand-craft one from a request id (BR-002-11). It holds `accountId`, `isAdmin`, `personas`, `memberships` (`officeId`, `readOnly`, `advisorPlanActive`), `clientLinks` (`active` or `ended`, with `endedAtMs`, epoch milliseconds so the frozen context holds nothing mutable; a pending invitation is never loaded, D-45), `selfAdvised`, `entitlements` and `readOnly` (false for an account's own requests; the support-grant contexts of part 3 set it), with `hasPersona()`, `hasEntitlement()`, `canWriteWith()`, `conductedOwners()` (`{ ownerType, ownerId }` of every office the account is a member of, plus itself when self-advised) and `writableOwners()` (read-only offices removed, BR-002-30).

- **Personas** are derived, never stored (BR-002-14, DL-002-03), in the pure `access/domain/personas.ts` (AR-05, 100% branch, TS-24): searcher for every active account; advisor for a member of an office whose advisor plan is active; investor for an active client link or a journey as investor; self-advised from its source. An admin context has no membership, link, self-advised status or entitlement even when a source returns some, and no persona but searcher (BR-002-21, BR-002-23: fail closed).
- **Seams.** The relationships come from four DI tokens, each read fresh on every request (AR-13, BR-002-15): `MEMBERSHIP_SOURCE`, `CLIENT_LINK_SOURCE` (SPEC-011; also `hasJourneyAsInvestor` for SPEC-016), `SELF_ADVISED_SOURCE` (SPEC-011) and `OFFICE_PLAN_SOURCE` (SPEC-012: per office `advisorPlanActive`, `readOnly`, `entitlements`, and the self-advised entitlements). The interfaces are `access/sources/*.ts`; `AccessModule` binds defaults that return nothing until the owning spec binds its own; `OFFICE_PLAN_SOURCE` is bound to SPEC-012's `SubscriptionOfficePlanSource` (below, §13). An office the plan source does not know has no plan, no entitlement and is read-only.
- **Guards** (opt-in per route or controller; each applies its guard and documents its 403): `@RequiresPersona(...)` (any of, `PERSONA_REQUIRED`), `@RequiresEntitlement(name, { write })` (`PLAN_NOT_ALLOWED` without it; with `write: true`, `OFFICE_READ_ONLY` when only read-only offices hold it, BR-002-30) and `@AdminOnly()` (`users.isAdmin`, `FORBIDDEN` otherwise; an admin whose email is not confirmed gets `EMAIL_VERIFICATION_REQUIRED`, SC-09).
- **An access requirement overrides `@Public()` (SC-07).** Each access decorator also sets `REQUIRES_ACCESS`; a route is anonymous only when `@Public()` applies (handler or controller) and no access requirement applies (handler or controller). `isPublicRoute` (`auth/decorators/public.decorator.ts`) is the one rule `JwtAuthGuard`, `AccessContextGuard` and `ConfirmedEmailGuard` apply, so a handler-level `@AdminOnly()` inside a `@Public()` controller authenticates (401 anonymous, 403 without the capability). The access guards never skip for `@Public()`: with no context they refuse with `UNAUTHENTICATED`. `test/structural/public-access-decorators.spec.ts` rejects `@Public()` with an access decorator on one handler or controller, and a `@Public()` handler in a controller with a requirement. These refusals are 403 because no record is involved; a record the caller may not access is still a 404 (AR-14). Plan limits are not a guard: they are counted with the write (AR-15).
- **Admin capability** is `users.isAdmin` (default false), read on every request, never the plan tier: the legacy `role: 'admin'` grants nothing, not the admin routes and not a paid feature (BR-002-23; migration `0004-admin-capability` copied it to the flag, and `role` is a legacy plan tier that SPEC-012 no longer writes, left in the schema until the contract step, AR-28). No API writes `isAdmin`; only the ops script `npm run grant-admin -- --email <address> [--revoke]` (`access/grant-admin/`, run from the build like `npm run migrate`) does, and it refuses an account with memberships, client links, journeys as investor or the self-advised status (BR-002-21), an unconfirmed email or a non-active account (SC-09). The grant write is conditional on the state it read and the relationships are re-read after it (an appearing one undoes the grant); SPEC-011's membership and link writes must mirror that, conditional on `isAdmin != true` (TOCTOU). A revoke also resets a legacy `role: 'admin'` to `'free'`, so a re-run of `0004` cannot re-grant. The four access sources are bound in `AccessModule` only — the API (through `AuthModule`) and grant-admin (`GrantAdminModule`) both import it, so they read the same implementations (`test/structural/access-source-bindings.spec.ts`). Coupons and maintenance use `@AdminOnly()`; `RolesGuard` and `@Roles` are gone.
- `GET /api/auth/me` answers `isAdmin` and `personas` from the context (the sign-in answers carry `isAdmin`); the frontend uses them to choose what to show, never as the control (AR-51).

**Owner-scoped data (SPEC-002 part 2, #2).** Every repository of a scoped collection extends one of two bases in `backend/src/access/`; each public method takes the request's `AccessContext` (from `@Access()`), never an owner or account id (AR-12, BR-002-11).

- **`OwnerScopedRepository<T>`** (owned collections, AR-11): `find(ctx, filter, { sort, skip, limit, session })`, `count(ctx, filter)`, `findById(ctx, id)`, `create(ctx, record, { actingOwner, session })`, `updateById(ctx, id, changes, { session })`, `deleteById(ctx, id, { session })`. Reads are `$and`-ed with the `$or` of `ctx.conductedOwners()` `{ ownerType, ownerId }` pairs, so a filter a subclass passes can narrow but never widen them; no owner matches nothing (a server-trusted `{ _id: { $in: [] } }`), never "no filter". `create` sets the owner from `ctx.resolveActingOwner(requestedOfficeId?)`: the only owner the account conducts, or the office it names among its own memberships (another is `NOT_FOUND`, BR-002-12; several and none named is `VALIDATION_FAILED` on `officeId`; none at all is `FORBIDDEN`). Only `AccessContext` can build that `ActingOwner`, and a repository refuses one resolved for another request. Writes are one conditional operation filtered by `ctx.writableOwners()`; a miss is `OFFICE_READ_ONLY` when the record is the caller's own (BR-002-30; it leaks nothing) and otherwise the module's not-found, identical for a foreign, a missing and a malformed id (AR-14). A payload or an update naming `ownerType`, `ownerId`, `_id` or an operator is a programming error (BR-002-01). Protected, for a subclass to expose under its own name: `findAsInvestor` / `countAsInvestor` (BR-002-05/07, through the pure `access/domain/investor-scope.ts` and `investorScopeFilter` in `access/owner-filter.ts`: an active link reads every record of that office whose investor is the account, an ended one only those closed at or before its end, plus the account's own self-advised records; nothing for an admin or a pending link) and `findAcrossOwnersForJob` (AR-12, BR-002-29; no caller yet).
- **`AccountScopedRepository<T>`** (an account's own data, BR-002-02): the scope is `userId $eq ctx.accountId` and nothing else, so no office ever reaches it (DL-002-08). `find`, `count`, `findOne`, `findById`, `create` (sets `userId`), `updateById(ctx, id, changes, condition)`, `deleteMany`, `deleteById(ctx, id, condition)`; subclasses build their own queries with `ownedBy(ctx, filter)`. A support grant opens client data only, never an account's own data (BR-002-02, BR-002-23, DL-002-04): its view (`ctx.viaSupportGrant`, read-only) is refused on **every** path before the database is touched — `find`, `count`, `findOne`, `findById` and every subclass query built on `ownedBy` throw the module's not-found (lists and counts too, never an empty answer, so a refusal is never mistaken for an account with no data), and `create`, `updateById`, `deleteMany`, `deleteById` throw `FORBIDDEN` (read-only). The cross-account job methods take no context, so a grant view cannot reach them. Jobs use the protected `findAcrossAccountsForJob`, `updateAcrossAccountsForJob` and `createForAccountByJob`. Favorites, saved filters, reminders and notification logs have their repositories (`FavoritesRepository`, `SavedFiltersRepository`, `RemindersRepository`, `NotificationLogsRepository`); their services take the context, and the reminders scheduler uses the named cross-account methods (`findDueAcrossAccounts`, `markSentAcrossAccounts`, `recordDeliveryByJob`). A malformed id now answers the module's 404 like a missing one.
- **Plan limits (AR-15, BR-002-13)**: `OwnerCounterRepository` (`OwnerCountersModule`, collection `ownerCounters`, unique `{ ownerType, ownerId, key }`): `ensureCounter(ctx, key, { actingOwner })` creates the zero counter if missing (never in a transaction, idempotent, a duplicate-key race ignored); `tryAcquire(ctx, key, limit, { actingOwner, session })` takes a slot in ONE conditional update (`value < limit` → `$inc`); `release(ctx, owner, key, { session })` never goes below zero and takes the owner as stored (a string or an `ObjectId` id). Without a session `tryAcquire` ensures the counter itself. **In a transaction the order is fixed** (SPEC-016, the journey insert): `ensureCounter` BEFORE `startTransaction`, then the transaction's writes and `tryAcquire(..., { session })`. A transaction reads the snapshot of its first operation, so a counter created after it is invisible and a conditional `$inc` would answer "limit reached" at zero; `tryAcquire` with a session therefore never creates the counter, and a counter it cannot see throws a programming error naming `ensureCounter`, never `false`. A release happens once per counted thing: the caller closes it with a conditional write (e.g. `status: { $ne: 'closed' }`) in the same transaction and releases only when that write matched, so a double close cannot give a slot back twice. The module joins the API with SPEC-012's `JourneySlotsService` (below, §13); migration `0007-billing-indexes` builds the unique `{ ownerType, ownerId, key }` index in the deploy (AR-29), and `readValue(ctx, key, { actingOwner })` is the owner-scoped READ of a count (it works for a read-only office too).
- **Private file links (SC-18)**: client files live in their own bucket, `R2_PRIVATE_BUCKET`, with no public access, never in `R2_BUCKET` (served openly at `R2_PUBLIC_URL`); the API refuses to boot when the two are the same. `StorageService.issuePrivateFileLink(key)` signs a GET of the private bucket valid for `PRIVATE_FILE_LINK_SECONDS` (60, not a parameter) for keys under `PRIVATE_FILE_PREFIX` (`private/`) only; it never builds a public URL, never logs the key or the link, and refuses when `R2_PRIVATE_BUCKET` is unset rather than falling back to the public bucket. `uploadBuffer`, `downloadBuffer` and `deleteFile` send a `private/` key to the private bucket (refusing while it is unset) and every other key to the public one; `getSignedUrl` refuses private keys. SPEC-017 is its first caller.
- **Adding an owned collection**: give the schema `ownerType` and `ownerId` (required, indexes starting `{ ownerType: 1, ownerId: 1 }`, AR-27), extend `OwnerScopedRepository`, and add `test/isolation/<name>.isolation.spec.ts` calling `isolationSpecFor('<ModelName>', ...)` that drives the API with two owners (TESTING §4). A collection without `ownerId` calls `markIsolation(schema, { kind, reason })` (`access/isolation-mark.ts`) right after `createForClass`: `'account'` (BR-002-02 data scoped by `userId`, needs an isolation spec too), `'internal'` (the account itself, sessions, tokens, sign-in attempts: read by the caller's own id, never listed) or `'public'` (catalogue and operations data). Marking an `ownerId` schema throws. The gate (AR-16, TS-14) fails the build otherwise.

**Support access grants (SPEC-002 part 3, #2).** The admin's only path to client data (BR-002-23, BR-002-24, DL-002-04) lives in `backend/src/admin-access/` (`AdminAccessModule`, in `FEATURE_MODULES` but with no controller yet).

- **Seam.** Support requests are SPEC-009's: `SUPPORT_REQUEST_SOURCE` (`access/sources/support-request.source.ts`, bound in `AccessModule` like the other sources and covered by `test/structural/access-source-bindings.spec.ts`) answers `findForGrant(id)` → `{ id, requesterUserId, open, dataAccessAllowed }` or null, read fresh on every call. Its default knows no request, so until SPEC-009 binds its own no grant can be opened.
- **Grants** (`supportAccessGrants`, marked `'internal'`): `supportRequestId`, `adminUserId`, `requesterUserId`, `openedAt`, `expiresAt` (= `openedAt` + 7 days), `status` (`open`/`ended`), `endedAt`, `endReason` (`closed`/`withdrawn`/`expired`). A partial unique index on `supportRequestId` where `status: 'open'` (MongoDB cannot filter a partial index on a missing `endedAt`, hence `status`) makes concurrent opens end with one grant. `SupportGrantService.open(adminCtx, supportRequestId)` needs `isAdmin`, an open request whose requester allowed data access, and a requester that is an active non-admin account (BR-002-21); every other case is the same `NOT_FOUND` as a nonexistent request (no oracle). It is idempotent for the same admin; a request whose open grant another admin holds is the same `NOT_FOUND` (no oracle: the answer never says a grant exists, nor whose it is). The partial unique index, like the log's indexes, is built by migration `0005-admin-access-indexes` in the deploy's migration step (AR-29, DV-34), not left to Mongoose's autoIndex; a unit spec holds the migration's specs equal to the schemas'. A grant is never edited: its one change is the end transition (`open` → `ended`, conditional, once).
- **Validity** (`admin-access/domain/grant-validity.ts`, pure, 100% branch): a grant ends at the first of request closed (or gone), permission withdrawn, or 7 days, a half-open interval `[openedAt, openedAt + 7 d)`: a read at exactly 7 days is refused, as is one at 7 days and 1 minute. `SupportGrantService.contextForRead(adminCtx, grantId)` re-checks it on **every** read against the current request and the injected `Clock` (AR-13, AR-24); a grant found ended is recorded (`endedAt`, `endReason`, conditional on still open) and refused with `NOT_FOUND`. Expiry needs no job: it is found lazily; SPEC-009 calls `endForSupportRequest(id, 'closed' | 'withdrawn')` when it closes a request or the requester withdraws. A grant is bound to its admin (another admin's id answers like a random one).
- **The grant's view (BR-002-25), sealed (BR-002-27).** On success `contextForRead` returns a `SupportGrantRead` (built by the service only) whose view is the requester's **current** context (`AccessContextFactory.forAccount`, their memberships and links of this request) passed through `AccessContextFactory.supportGrantView`: read-only and marked `viaSupportGrant`. It reads exactly the **client data** the requester reads — a member's office, an investor's own journeys as they see them — and nothing of the requester's own account data. Refusals: owned writes are `OFFICE_READ_ONLY` on the requester's own records and the module's not-found otherwise (OwnerScopedRepository); account-own data (favorites, saved filters, reminders, `AccountScopedRepository`) answers the module's not-found to every read and `FORBIDDEN` to every write. The view is **not a property** of `SupportGrantRead`: it is sealed in a WeakMap (`admin-access/grant-context.ts`) that only `GrantReadLogger` opens, so a handler cannot read with it and skip the log; `test/structural/support-grant-seal.spec.ts` fails the build on any other use of `grantContextOf`, `sealGrantContext` or `supportGrantView`.
- **Logged reads, fail closed (BR-002-27).** `adminAccessLogs` (marked `'internal'`, insert-only, AR-30): `adminUserId`, `action` (`grant_read`, later SPEC-009's `account_search`/`account_view`), `grantId`, `supportRequestId`, `owner { type, id }`, `resource { type, id }`, `query` (account searches only: SPEC-009 must keep personal data out of it or justify it in SECURITY §9), `at`, indexed `{ adminUserId, at }` and `{ 'owner.id', at }`. Its repository exposes `append` only, schema middleware throws on every update, replace, delete, bulk write and re-save, and `test/structural/admin-access-append-only.spec.ts` fails on any such call in `admin-access/` other than the grant's end transition — and on any way below Mongoose: the names `adminAccessLogs`/`supportAccessGrants` as a string outside the two schemas and migration 0005, `$merge`/`$out` anywhere in `src/`, any `drop`/`dropCollection`/`dropDatabase`/`dropIndex(es)`/`renameCollection` call, and `.collection`/`.db`/`.connection` or an injected connection inside `admin-access/` — and, anywhere else in `src/` (the schemas, repositories and migration 0005 aside), any lookup, injection or naming of the two models or collections: `connection.model`/`db.model`/`mongoose.model`, `connection.models`/`.collections`/`modelNames`, `@InjectModel`, `getModelToken`, `.collection(...)`, the entity class symbols, with static spellings resolved and an unresolvable argument refused. The control that holds beyond our own code is the API's database role (SECURITY SC-09). `GrantReadLogger.readOne` / `readMany` run the load with the grant's context, append **one entry per record returned** (one `insertMany` for a list) and only then hand the records back; if the append fails they throw `AdminAccessLogUnavailableError`, a fault answered as a bare `500 INTERNAL_ERROR` with no data. A read writes nothing else, so it needs no transaction: the log is acknowledged before any byte of the record is sent.
- **The route pattern** for SPEC-009 (open, list and end grants), SPEC-016 and SPEC-021 (the read services): `/api/admin/support-grants/:grantId/...`, every handler `@AdminOnly()`, first `contextForRead(ctx, grantId)`, then the module's ordinary **owner-scoped** repository or read service called with the view `GrantReadLogger.readOne`/`readMany` hands its load (`ownedRecordRead('<type>')` describes an owned record), returning only what the wrapper returned; write handlers do not exist, and account-own data has no grant route (its repositories refuse the view). An admin hitting the ordinary client routes still gets `404`/`403`, grant or not. `test/isolation/support/probe.module.ts` (`ProbeAdminGrantController`) is the working template, proven by `test/isolation/support-grants.isolation.spec.ts`.
- **Log hygiene (BR-002-28, DL-002-07).** `test/isolation/log-hygiene.isolation.spec.ts` seeds markers into an account name, a profile change, a support request, a saved filter, a reminder note and an owned record, runs the flows (refusals, a grant read, a fault, the reminders job) and finds none in any Nest Logger call or stdout/stderr write (`captureAllLogOutput`), in any line the production logger writes (nestjs-pino with the API's `loggerParams` at level info, into memory: pino-http completion lines and serialized errors), or in any error answer.

## 5. Money and precision

## 13. Data flows worth knowing

**Caixa import (SPEC-004).** Daily list download → parse (`domain/`) → validate → upsert with change detection → Import Run record. Detail-page enrichment runs separately, under a daily budget (pages per day, concurrency, pause), refreshes pages on a rolling basis, and **stops the run on any block or challenge** without trying to get around it (BR-004-18, BR-004-20, SC-24). Detail pages are fetched with plain `puppeteer` (no stealth plugin, no spoofed identity). npm 11 blocks dependency install scripts, so puppeteer's postinstall Chrome download is not relied on: the production image installs Chromium explicitly and points puppeteer at it (`PUPPETEER_EXECUTABLE_PATH`; `backend/Dockerfile`, DEVELOPMENT §12); locally, `npx puppeteer browsers install chrome` installs the browser once.

**Files (SPEC-017).** Upload and download through R2 presigned URLs, issued per request after an authorization check and valid for 60 seconds (BR-002-08, BR-002-09). Keys are random; nothing about the owner or the file's content appears in a key. Client files live in the private bucket `R2_PRIVATE_BUCKET`, which has no public access (no public URL, no custom domain) and is never `R2_BUCKET`; it must be created, and the variable set in `deploy-production`, before SPEC-017 ships (owner action).

**Maintenance windows (SPEC-003 BR-003-03).** An admin announces scheduled maintenance in the product (`POST /api/maintenance`, `maintenance/`, collection `maintenancewindows`, indexed on `startsAt`; `GET` lists and `DELETE` cancels a window that has not started). `announcedAt` is set from the injected `Clock` at creation and is never accepted from the client. Less than 48 h notice is allowed (urgent security patches, DL-003-03) but the window is `announcedInTime: false` and counts as downtime; `maintenance/domain/maintenance-window.ts` (`countsAsExcluded`, `isExcludedAt`) is what the availability report (BR-003-01, #115) reads: only a window announced at least 48 h ahead excludes anything, only between its announced start and end, so an overrun is downtime from the announced end. `GET /api/maintenance/upcoming` is public (`@Public()`, SC-07), carries no account data, and is cached 30 s (service and `Cache-Control`).

**Payments and subscriptions (SPEC-012, [ADR-005](../adr/005-office-subscriptions-on-stripe.md)).** An advisor plan belongs to an **office** (BR-012-06), and the payment provider is the source of truth for it. No user endpoint sets a plan, a state or a limit (BR-012-14): `PaymentsController` holds only the signature-verified webhook, which hands the raw body to `SubscriptionsService`; the old user-level checkout, status and cancel routes, the `STRIPE_STANDARD_PRICE_ID` setting and every write of `users.role` / `subscriptionStatus` / `stripe*` are gone (the fields stay in the schema until the contract step, AR-28).

- **Catalog** (`plans/`, collection `plans`, marked `public`): `code` (unique), `name`, `price` (Decimal128 reais, AR-17), `interval`, `activeJourneyLimit`, `stripePriceId` (unique), `status` (`OFFERED` / `WITHDRAWN`), `sortOrder`. Operators maintain it with `npm run plans:upsert -- --file <catalog.json>` (`plans/upsert/`, run from the build like `grant-admin`): Zod-validated, idempotent by `code`, refuses a provider price that is another plan's and a changed price id for an existing code (a new price is a new code; subscribers keep paying the old one), prints counts only. `GET /api/plans` is public and lists the offered plans as `{ items, refundWindowDays }` (the AR-35 lookup exemption; the refund window is `REFUND_WINDOW_DAYS`, so the plans page words its notice from the setting). Editing or withdrawing a plan never touches a subscription: each holds its own copy of the limit (BR-012-04).
- **Subscriptions** (`subscriptions/`, collections `subscriptions` and `paymentEvents`, both `internal`): the subscription is keyed by `officeId` (absent until the first payment is confirmed, BR-012-07), its `_id` is the **ref** we put on the provider's checkout and subscription, and it holds the plan copy, the provider ids, the period, `firstPaidAt`, `lapsedAt` / `readOnlyAt`, the sync lease and no amount. Indexes (built by migration `0006-subscription-indexes`, AR-29): `stripeSubscriptionId` and `checkoutSessionId` unique sparse; `officeId` unique **partial** on an existing office and a status in effect (`ACTIVE`, `PAST_DUE`, `CANCELING`), so two subscriptions in effect for one office cannot exist (BR-012-08); `paymentEvents.stripeEventId` unique.
- **Webhook algorithm** (`SubscriptionsService.handleProviderEvent`, BR-012-13, SC-11). The `PaymentGateway` port speaks our vocabulary (`Date`, reais as `Decimal`, ids): the Stripe adapter verifies the signature over the raw body (only a signature failure is `INVALID_WEBHOOK_SIGNATURE`; a failure to map a verified event is a 5xx fault, logged by code only), ignores an event of the other mode than the key (test vs live) as `unhandled`, and maps an event to ids only (`checkout.completed`, `subscription.changed` for created / updated / deleted, `invoice.paid`, `invoice.payment_failed`, `checkout.expired` with the session id, `unhandled`). `retrieveSubscription(id)` returns the provider's current snapshot and refuses a subscription without exactly one item; the client has an 8 s timeout and 2 retries so a read ends before the 30 s lease can be taken over. (1) The event is recorded by its provider id in `paymentEvents`: a repeat of a **processed** event is acknowledged and does nothing; a repeat of an **unprocessed** one (a crash or fault midway) is handled again, because the sync is idempotent; `processedAt` is set only after the event was handled in full. (2) Every subscription event runs `syncFromProvider`: resolve our record (by the provider id, else by the ref in the event, else by the ref the provider's own subscription carries, so an event that arrives before `checkout.session.completed` still finds it). A subscription with **no** ref is legacy user-level and is acknowledged and ignored with a warning; a ref that names no record, a ref that does not match its record, and a first activation on a price no plan maps to are **faults** (5xx, id-only warning), never acknowledged. (3) Take a **per-record lease** (one conditional update on `syncLeaseUntil`, 30 s), **retrieve inside it**, map the snapshot with the pure `subscriptions/domain/provider-state.ts` and write it conditional on still holding the lease token, releasing the lease in the same write. (4) **A delivery that finds the lease taken is not refused**: it does one conditional update (`syncRequestedAt`) that matches only while a lease is live and is done. The holder's write returns the document as it was, so it sees atomically whether a request arrived before the release; if so it reads the provider again (at most 3 reads, then `WEBHOOK_BUSY`). A request after the release matches nothing and its sender takes the lease itself (3 attempts, then `WEBHOOK_BUSY`). So every read that follows an event happens after that event, bursts are coalesced and there is no delayed 503. A payment-failed event that was only covered answers `WEBHOOK_BUSY` so that its retry makes the email decision from its own read. After each sync the stored state equals what the provider said at that read, whatever order the events came in; a record can still lag the provider until the next event or read, and the daily reconcile job heals lost events (below). (10) **The same event twice at the same moment** (SC-11): after `record`, a delivery claims the event (`processingToken` / `processingUntil` on the ledger document, one conditional update, 2 minutes); the loser answers `WEBHOOK_BUSY` and its retry finds the event processed; a failed delivery releases its claim at once, a holder that died loses it when it expires. (5) State mapping: `active` / `trialing` → `ACTIVE` (`CANCELING` when renewal was stopped), `past_due` → `PAST_DUE`, `unpaid` / `canceled` / `incomplete_expired` / `paused` → `LAPSED`, `incomplete` → `PENDING`; `lapsedAt` is set on entering `LAPSED` (the provider's end instant, else now), kept while lapsed and cleared on leaving; `firstPaidAt` is set once from the provider's paid time. Plan and limit change only when the provider bills another price than the plan the record is on (a withdrawn plan still resolves by its price id), which with `pending_if_incomplete` is only after an upgrade's proration is paid (BR-012-16); a downgrade scheduled for the next period is read from the subscription schedule (BR-012-17). (6) A subscription that is in effect and has no office gets one through the `OFFICE_PROVISIONER` port, then a conditional attach (a different office answered by the port than the one kept is logged with ids). - **Consent generations (DL-001-02).** Someone who registers an address by e-mail without ever confirming it can leave acceptances and a WhatsApp consent behind that the real owner, signing in with Google, would inherit. `users.consentResetAt` (protected, server-written) closes that: the Google takeover of an unconfirmed account sets it to the Clock instant and clears `whatsappPromptAnsweredAt` in the SAME atomic pipeline update that deletes the password and bumps `credentialVersion` (`UsersService.linkGoogleIdentity(userId, googleId, now)`, pure table in `users/domain/google-link.ts`); linking a confirmed account changes neither. Every `consents` and `whatsappConsents` row carries the `consentResetAt` in force when it was written (null: never reset), and only rows of the account's CURRENT value exist for it: `pendingFor`, the account's acceptance list, the WhatsApp state and `hasConsent` all filter on it, so the registrant's rows stay as history and count for nobody, and the owner is asked to accept (under enforcement) and to answer the one-time request again. The value is part of the unique key (`{ userId, consentResetAt, documentType, version }`), so the owner can accept a version the registrant had accepted. A sign-up passes `null` as the generation of the account it just created (never re-read), so a registrant's request that finishes after the takeover writes under the old generation and counts for nobody; `markWhatsappPromptAnswered` is conditional on the generation too. A signed-in request carries its generation with the account (`AuthenticatedUser.consentResetAt`, read by `JwtStrategy`); `hasConsent(userId)` reads it from the account.
- **Sign-up**: `RegisterDto` and `GoogleCompleteDto` keep `acceptTerms: true` and take optional `termsVersion`, `privacyVersion` and `whatsappConsent`. Order: validate versions (before anything exists, and for Google before the code is spent) → create the account **`pending`** → record the acceptance and the WhatsApp answer → activate it with ONE conditional update (`UsersService.activateAccount`, `{ _id, status: 'pending' } → { status: 'active' }`). A `pending` account authenticates nothing: every check of the status goes through `isAccountActive` (`users/user-account.ts`: a missing status is active, AR-28; `pending`, `deactivated` and `closed` are not) and every conditional write of the account carries the matching filter, so no sign-in (password, Google exchange or link, session, reset request, confirmation, admin grant) can find an account whose consent records do not exist yet, whatever the interleaving, and nothing can be issued for it. If a step fails the account is rolled back (`UsersService.discardUnfinishedSignup`: `deleteOne({ _id, status: 'pending' })`, the undo of a failed creation, not an AR-31 deletion of a person's data; an account that became active meanwhile is never deleted, and no credential-version heuristic is needed); the log names the kind of failure only, the original error is rethrown, and the address is free to try again (for Google the code is spent, so the person signs in with Google again). When the rollback itself fails the account stays `pending`, unable to sign in; a sign-up (e-mail, or Google sign-in and completion) that collides with a `pending` account older than `PENDING_SIGNUP_TTL_MS` (15 minutes, from the injected Clock, so `createdAt < now − 15 min`) deletes it conditionally (`status: 'pending'` and the age in the same `deleteMany`, `UsersService.discardAbandonedPending`) and proceeds; a younger one answers as a taken e-mail (`EMAIL_ALREADY_REGISTERED`) and, for Google, as `GOOGLE_SIGN_IN_FAILED` with no session. Existing accounts have no `status` or the value `active`: no migration is needed. Declining Google stores nothing (`google/cancel`). A Google completion that finds an account created meanwhile records nothing for it.
- **WhatsApp consent** (`whatsappConsents`, `internal`, insert-only): one row per answer (`action` `granted` / `withdrawn` / `declined`, `method` `signup` / `existing_account_prompt` / `privacy_page`, `textVersion` = `WHATSAPP_CONSENT_TEXT_VERSION`, `at`); the state is the latest row. `WhatsappConsentService.hasConsent(userId)` (exported for SPEC-008 and SPEC-025) is true only for a latest `granted`; consent never creates a message by itself. The sign-up checkbox is unticked by default and recorded either way (declined is a row) and never blocks the account (BR-010-27). Any answer sets `users.whatsappPromptAnsweredAt` (set once; protected field, written only by this service), and `/auth/me` carries `whatsappPromptPending` until then: an account that predates the channel is asked once. Answering what the latest answer already says is not recorded again (the state is returned and the prompt still marked answered). Routes: `GET` and `POST /api/privacy/whatsapp-consent` `{ action, method: 'existing_account_prompt' | 'privacy_page' }`.
- **The current-terms guard** (`CurrentTermsGuard`, the third global guard in `AuthModule`'s providers, after `JwtAuthGuard` and `AccessContextGuard`; `jwt-auth.guard.spec.ts` holds the order): with `TERMS_ENFORCEMENT_ENABLED` on, an authenticated non-public route of an account whose current terms or policy are not accepted answers 403 `TERMS_ACCEPTANCE_REQUIRED` with `{ documents: [{ type, version }] }` (ids and versions only, AR-40). `@AllowWithoutTerms()` (handler or controller) exempts `GET /auth/me`, `POST /auth/logout`, `GET /auth/profile/full`, `PATCH /auth/profile` (access and correction, BR-010-08, BR-010-12), `/legal/*` and `/privacy/*` and nothing else (`test/structural/allow-without-terms-routes.spec.ts` pins the exact set), so the acceptance and the rights of BR-010-08..13 never wait for it (DL-010-03). Off (the default), the guard answers at once and reads nothing. `GET /api/auth/me` answers `termsAcceptanceRequired`, `documents` (empty when up to date) and `whatsappPromptPending` whether or not the guard enforces.
- **Indexes**: migration `0008-consent-indexes` builds `consents.one_acceptance_per_version` (unique on `{ userId, consentResetAt, documentType, version }`) and `whatsappConsents { userId, consentResetAt, at: -1 }` (AR-29); `privacy/schemas/consent-indexes.spec.ts` holds them equal to the schemas', `test/integration/consent-indexes-migration.spec.ts` runs it twice. No migration erases the legacy CPF, date of birth, sex and address (an open owner decision, SECURITY §9).
- **Tests**: `test/integration/privacy.spec.ts` (sign-up and Google acceptance, stale version creates nothing, a v0.2 published later with the guard on and off, 20 parallel accepts, the WhatsApp prompt and withdrawal, insert-only), the Google takeover scenario, the rights and public routes under enforcement, `test/isolation/privacy.isolation.spec.ts` (A never reads or changes B's acceptances or consent, BR-002-11) and the privacy flows in `log-hygiene.isolation.spec.ts` (no name or e-mail in any log or error).

**Data-subject rights (SPEC-010 part 2, #10).** `PrivacyRightsModule` (`backend/src/privacy/rights/`, in `FEATURE_MODULES`) sits above `AuthModule` (closure needs re-authentication, sessions and links) and below nothing that imports it; the registry lives in the dependency-free `PersonalDataRegistryModule` (`privacy/registry/`). Operations are in the [account-purge runbook](../runbooks/account-purge.md).

- **Registry (SC-27).** `PersonalDataProvider { name, models, collect(ctx), purge(userId) }`; every module that holds a person's data registers one in its own constructor, through its own repository (AR-09): `account` (users), `sessions` (and the sign-in attempt counter keyed by the address), `accountTokens`, `favorites`, `savedFilters`, `reminders`, `notificationLogs`, `acceptances`, `dataExports`, `actorPseudonyms`. `collect` reads under the request's `AccessContext` (never more than the account sees as itself, BR-010-10) and returns plain values (money as strings, no password hash, token hash or session id); `purge` is idempotent and job-only. The registry refuses a name that is not a plain identifier or that the export envelope owns, a duplicate, a model two providers claim and a model the retained list names. `RETAINED_MODELS` declares what the purge keeps on purpose, each with its rule: `subscriptions` (BR-010-22, `buyerUserId` is an id only), `adminAccessLogs` and `supportAccessGrants` (BR-010-23), `consents` and `whatsappConsents` (proof records, still exported; `AcceptancesPersonalData` claims no model), `maintenancewindows` (`createdBy` is an operator id). The meta-test `test/isolation/personal-data-registry.isolation.spec.ts` boots `FEATURE_MODULES` and fails, naming the model, when a model with `userId`, `requesterUserId`, `authorUserId`, `buyerUserId`, `adminUserId` or `createdBy` is covered by neither a provider nor the retained list, or when a retained entry or a provider names a model that does not exist or both claim one. A new owned or account collection decides its provider in its own PR.
- **My data and export (BR-010-08..11).** `GET /api/privacy/my-data` answers `{ schemaVersion: 1, generatedAt, <provider>: ... }` at once, with each list bounded to 200 records (`MY_DATA_LIST_LIMIT`: providers read only that many through `collect(ctx, { limit })`, `capSections` is the net for any that do not): a cut section says `truncated: true` and `totals: { items: <how many there are> }` and the interface points to the export, which is COMPLETE (BR-010-08, BR-010-09) and reads the account's lists in pages of 500, never one unbounded query; `POST /api/privacy/exports` queues the one live export of the account (partial unique index `one_live_export_per_user` on `live: true`, set while queued or ready, so twenty requests at once end with one row; a ready export past `expiresAt` that the hourly job has not reached yet is ended where it is found, `expireNow`, so the owner can ask for a fresh one), `GET /api/privacy/exports` lists them (AR-35) and `GET /api/privacy/exports/:id/download` issues `StorageService.issuePrivateFileLink` (60 s) to the owner only: another account's id, a missing and a malformed one are the same `404 NOT_FOUND`; `EXPORT_NOT_READY` (409) while queued, `EXPORT_EXPIRED` (410) from `expiresAt = readyAt + EXPORT_TTL_DAYS` (half-open: 7 days and 1 minute is refused; pure `domain/data-export.ts`). `DataExportJob` (`*/2 * * * *`, run-level lock in `jobLocks`) claims the oldest queued export (a lease), chooses its random key `private/exports/<random>.json` in the same update and BEFORE writing any file, builds the JSON under `AccessContextFactory.forAccount(userId)` for an ACTIVE account only, uploads to the private bucket (without `R2_PRIVATE_BUCKET` the export is `failed` with `EXPORT_STORAGE_UNAVAILABLE`, never the public bucket, SC-18) and marks it ready with ONE update conditional on `status: 'queued'` and the claim: when it matches nothing the worker looks at its row: gone (the purge deleted it) or no longer live (a closure cancelled it) means it deletes the file it wrote under its own key; still live means another worker took the lease over and owns the key, so the file is left. A failure NEVER removes the `fileKey` from the row (the key is chosen before any write, and a crashed earlier worker may have uploaded under it): the cleanup deletes the file, which is idempotent, and only then clears the key. The cleanup and the purge both leave alone a row whose worker lease (`claimUntil`) is still live: the purge of that account fails for now (`ExportBuildInProgressError`, claim released) and the next run finishes it. `expireDue` (hourly) deletes the file of a ready export past its time and marks it expired, and the files still named by failed, cancelled and expired rows. Only counts are logged (SC-15).
- **Closure (BR-010-13, BR-010-14).** `POST /api/privacy/delete-account` `{ password | googleCode, confirm: true }` (exactly one proof, throttled per account like the other privacy routes, exempt from the terms guard). `AuthService.reauthenticate`: the password path reserves a `loginAttempts` slot like change-password (`CURRENT_PASSWORD_INCORRECT`, `TOO_MANY_ATTEMPTS`); the Google path spends a fresh `google_exchange` code (60 s, atomic, single use) only if it belongs to the CALLER (another account's code is `INVALID_GOOGLE_CODE` and stays unspent); no password and no Google is `REAUTHENTICATION_UNAVAILABLE`. `UsersService.closeAccount` is ONE conditional update `active | deactivated -> closed` that sets `closedAt` (Clock) and bumps `credentialVersion` (SC-03), so a sign-in that passed its checks just before cannot keep a session (status and version both refuse it) and of two closures at once exactly one wins; the loser, whose re-authentication may find the account closed, answers the same success and runs nothing. Then the effects, each attempted and idempotent: `AuthService.endAllSessionsAndLinks`, `DataExportsRepository.cancelLiveOf` (queued AND ready exports become `cancelled`; the key and the worker's claim stay, for the file cleanup and the purge to respect), `RemindersService.cancelPendingOfAccount` (pending reminders become `CANCELLED`, which the scheduler's due query never selects, so a closed account's backlog cannot crowd out another account's page of 50 due reminders; the due query also orders by `scheduledAt`, and the scheduler cancels a closed or missing account's reminder it still meets; a deactivated account's stay pending, since it may come back) and the `ACCOUNT_CLOSURE_HOOKS` (bound to none in `PrivacyRightsModule`; SPEC-011 ends client links and memberships, SPEC-012 billing steps; hooks must be idempotent). A failing step is logged by name and never undoes the closure; the purge repeats all of them, and a failing registered HOOK there fails the account's purge (`ClosureHookFailedError`: no provider runs, no tombstone, claim released, next run retries), because the links and memberships a hook ends must be over before the data is erased. A recovery link spent after the closure rewrites nothing: `resetPassword` answers the generic `INVALID_RESET_TOKEN` and the password write is conditional on an active account. Nothing is deleted inline (AR-31). Every sign-in method refuses a non-active account, the reminders scheduler skips it, and its address cannot be registered again until the purge. No address under the reserved `.invalid` domain (RFC 6761) is accepted anywhere (`EmailField`, `createLocalAccount`, `createGoogleAccount`: `VALIDATION_FAILED` on `email`), so nobody can squat the tombstone namespace; and if the plain tombstone address is taken anyway, `completePurge` retries with `purged-<id>-<random hex>@removed.invalid` and never fails the purge for that.
- **Purge (BR-010-15).** `AccountPurgeJob` (`10 4 * * *` Brasília, `@InJobContext`, `ACCOUNT_PURGE_ENABLED`, run-level lock `job:account-purge`, `jobexecutions`): candidates are `status: 'closed'` without `purgedAt` and without a live claim, oldest `closedAt` first, read 100 at a time (`PURGE_BATCH_SIZE`) up to 500 attempts a run (`PURGE_MAX_ATTEMPTS_PER_RUN`); an account that fails or is skipped is left out of the rest of the run, so a permanently failing head of the queue never stalls the accounts behind it. Per account: atomic claim (`purgeClaimToken`, 10-minute lease, one conditional update), the closure effects again (repairs a crash between closure and them), `PersonalDataRegistry.purge(userId)` (providers in turn), then the tombstone, conditional on the claim and written LAST (`UsersService.completePurge`): `PURGE_REMOVED_FIELDS` unset (name, phone, googleId, password, providers, emailVerified, isAdmin, legacy CPF, date of birth, sex, address and billing ids), email replaced by `purged-<id>@removed.invalid` (which frees the address), `purgedAt` set, `_id`, `status`, `closedAt` kept. A failure at any step releases the claim and leaves the account unpurged; the next run repeats every step, so a crash anywhere converges (fault injection at every provider, at the tombstone and with a dead worker's lease is in `test/integration/account-purge.spec.ts`). The `dataExports` provider deletes each file before its row; `actorPseudonyms` is detached, not deleted. The alert is its own daily check (`checkOverdueDaily`, `20 4 * * *`, own `@InJobContext`, NOT behind `ACCOUNT_PURGE_ENABLED`, so a switched-off or broken purge still raises it): `Logger.error` with a count when a closed account is unpurged `ACCOUNT_PURGE_ALERT_DAYS` after `closedAt`. Backups keep deleted data until they rotate: retention must stay at 30 days or less, or a restore replays the purges ([runbook](../runbooks/backup-and-restore.md#restore-replay-the-purges)).
- **Pseudonyms (BR-010-28).** `ActorPseudonymService.forPerson(journeyId, userId)` (exported by `PrivacyRightsModule` for SPEC-011 and SPEC-016) returns a stable random label (`p-` and 128 random bits as hex, derived from nothing about the person) per person and journey, find-or-insert race-safe on the unique `{ journeyId, userId }` index (partial on an existing account); `detachUser(userId)` sets `userId: null` on the person's rows at purge, so no row references them and the label cannot be traced back. Two people of a journey differ, one person has another label in another journey.
- **Race rules.** (a) closure: the conditional status update; (b) sign-in: status plus credential version; (c) export: conditional `queued -> ready` and `cancelLiveOf` in either order end `cancelled`, and the loser of the former deletes its file; (d) purge: run-level lock plus per-account claim; (e) purge: resumable and idempotent at every step, tombstone last and conditional on the claim; (f) a sign-in during the purge is refused (the account is closed); (g) one live export per account by a partial unique index; (h) an address is free only after the tombstone replaces it.
- **Indexes and fields**: migration `0009-privacy-rights-indexes` builds `dataExports` (`one_live_export_per_user`, the account's list, the worker's queue and the expiry scan), `actorPseudonyms` and `users { status, closedAt }`; the user schema gains `closedAt`, `purgedAt`, `purgeClaimToken`, `purgeClaimUntil` (protected from profile writes). New collections `dataExports`, `actorPseudonyms`, `jobLocks` are `internal`. New codes `REAUTHENTICATION_UNAVAILABLE`, `EXPORT_NOT_READY`, `EXPORT_EXPIRED`.
