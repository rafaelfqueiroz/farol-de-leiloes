## 2. TypeScript

|           |                                                                                                                                                                                                          |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-01** | `strict: true` on both packages, with nothing relaxed (`noImplicitAny` stays on), plus `noUncheckedIndexedAccess`, `noImplicitOverride` and `noFallthroughCasesInSwitch`.                                |
| **DV-02** | `any` is banned by lint (`@typescript-eslint/no-explicit-any: error`). `unknown` plus validation is the escape hatch. A genuinely necessary `any` carries an `eslint-disable-next-line` with the reason. |
| **DV-03** | No non-null assertions (`!`). If a value can be absent, handle the absence.                                                                                                                              |
| **DV-04** | Inference inside functions; explicit types at boundaries — exported service methods, repository methods, `domain/` functions, controller handlers and React component props.                             |

## 3. Runtime and packages

|           |                                                                                                                                                                                                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-05** | **Node 24 LTS, one exact version, pinned everywhere**: `.node-version` at the root and in each package, `engines.node` in both `package.json`s, the Docker images by tag, and `node-version-file` in CI. ## 4. Naming and structure

|           |                                                                                                                                                                                                                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-07** | Backend files are `kebab-case` with the Nest role suffix: `journey-phase.service.ts`, `create-journey.dto.ts`, `journey.schema.ts`. React components are `PascalCase.tsx`; other frontend files `kebab-case.ts`.                                                                                     |
| **DV-08** | Directories are domain concepts (`journeys/`, `viability/`), lowercase with hyphens. Never `services/`, `helpers/`, `utils/` at module level.                                                                                                                                                        |
| **DV-09** | Frontend imports use the `@/` alias. Backend imports stay relative inside a module; another module is reached only through its exported service (AR-09).                                                                                                                                             |
| **DV-10** | No barrel files (`index.ts` re-exports) except a module's public surface. They hide the import graph the boundary lint depends on.                                                                                                                                                                   |
| **DV-11** | Never `console.*` — use NestJS `Logger` (AR-45). Enforced by ESLint `no-console: error` in both packages. In the frontend, handled client errors go through `reportClientError` (`frontend/lib/report-client-error.ts`), which logs only `[where] Name: message`; it sends to Sentry once #36 lands. |
| **DV-12** | Prettier owns formatting (2 spaces, semicolons, single quotes, trailing commas, 100 columns). Nobody formats by hand and no review comment is about formatting.                                                                                                                                      |

### Migrations

Backfills and data reshapes (AR-28, AR-29) are migrations in `backend/src/migrations/`, run by an in-house runner ([ADR-001](../adr/001-in-house-mongodb-migrations-runner.md)).

**Writing one.**

1. Add `NNNN-short-title.migration.ts`, the next number, exporting a `Migration`: `{ id: 'NNNN-short-title', description, up(db) }`. `up` uses the driver (`mongo.Db`) and names its collections; it never imports a schema or model, so it keeps doing what it did when it was written.
2. Make `up` **idempotent**: select only documents still in the old shape (for a type change, `$type` on the old BSON types — never the `'number'` alias, which also matches `decimal`), and make each write conditional on the value read. The runner records a migration only after `up` resolves, so one that failed halfway runs again from the start. See `0001-money-decimal128.migration.ts`.
3. Append it to `MIGRATIONS` in `registry.ts`. Never insert before, edit or remove an applied migration — migrations are forward-only; a mistake is fixed by a new one.
4. Test it: unit specs for its conversions with hand-computed values (TS-04), and an integration spec that seeds the old shapes, documents already converted and nulls, runs it twice and asserts the second run changes nothing (`test/integration/migrations.spec.ts`).
5. Log counts only, never document content (SC-15).

**Running one.** `npm run migrate` reads the same validated environment as the API (AR-41) and refuses to run with an invalid one. It applies every migration not yet recorded in the `migrations` collection, in order, records each with its `appliedAt`, and stops at the first failure with exit code 1, leaving that migration unrecorded; running it again is safe. It is the gated step **before** new code starts (DV-34): the code of a contract step reads only the new shape and fails loudly on the old one. Once the deploy job in `deploy.yml` is turned on (`DEPLOY_ENABLED`, §12), it runs the same runner as its gated step, in the `migrate` service of `deploy/compose.production.yml`. Until then (BL-001, [#40](https://github.com/rafaelfqueiroz/farol-de-leiloes/issues/40)), **the owner runs it by hand from their machine against the production database (MongoDB Atlas), before merging code that depends on it**. Like the API, it loads `.env` from the current directory (`@nestjs/config`), and variables already set in the process environment take precedence. To target production, pass Node an env file whose `MONGODB_URI` is the production cluster. Keep that file as the gitignored `backend/.env.production`. The command is `npm run build && node --env-file=.env.production dist/migrations/run.js`, run in `backend/`. Every variable the API requires must be in that file, because the environment is validated. Agents never run it: it writes to a real database (DV-19); their migrations run in Testcontainers through `test:integration`.

### Git hooks

| Hook         | Runs                                                                                                                                        | Scope                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `pre-commit` | lint-staged: `prettier --write`, `eslint --fix` (each package's own binaries and config; config in each package's `lint-staged.config.mjs`) | Staged files                                                         |
| `pre-push`   | `npm run check`                                                                                                                             | Each package each pushed ref changes, on the pushed revision (DV-37) |

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-37** | A **pre-push** hook runs `npm run check` in each package the push changes. It measures **every pushed ref** (so `git push other-branch` and `--all` are covered, whatever is checked out), against that ref's current remote revision (for a new remote branch, or a force-push over a revision not available locally, against its merge-base with `origin/main`). It checks the revision being pushed: in place when that is the checked-out HEAD and the package has no uncommitted changes, otherwise in a temporary detached worktree (full `npm ci`) that is always removed. A change under `backend/` checks the backend; a change under `frontend/` checks the frontend; a change to shared root files (`.node-version`, `docker-compose.yml`, the hook tooling) checks both; a push that touches only `docs/` or `.github/` checks neither. Integration, isolation and E2E suites stay in CI: they need Docker and are too slow for every push. A failing hook blocks the push, and the failure is fixed, never bypassed (TS-30). |

The one-off formatting commit is listed in [`.git-blame-ignore-revs`](../../.git-blame-ignore-revs) (GitHub honours it; locally run `git config blame.ignoreRevsFile .git-blame-ignore-revs`). A later commit that only reformats code is added there too.

### Rules for AI coding agents

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-17** | Agents may run the package scripts above on the host: `check`, `test`, `test:integration`, `test:isolation`, `test:cov`. Databases always come from containers (Testcontainers picks random ports, so they never collide with the developer's own). `test:integration` and `test:isolation` need Docker running; when it is not, they stop with a "Docker is required (DV-17)" message — report that, never work around it by pointing a test at a local MongoDB (DV-19). |

E2E runs through `test:e2e`, which brings up its own Compose stack.                                                                                                                                                                                                                                                                           |
| **DV-19** | Agents never read, print or edit `.env` / `.env.local`, and never point a test at the developer's local database.                                                                                                                                                                                                                                                                                                                                                         |
| **DV-20** | An agent's work is not done until `npm run check` passes in every package it touched (the pre-push hook enforces this, DV-37), and the docs it affects are updated in the same PR (§9).                                                                                                                                                                                                                                                                                   |

## 7. Software development lifecycle

Product intent lives in the [wiki](https://github.com/rafaelfqueiroz/farol-de-leiloes/wiki): the PRD in Portuguese, the specs (`SPEC-NNN`) in English. Implementation is tracked on the [project board](https://github.com/users/rafaelfqueiroz/projects/4) — one issue per spec, titled `SPEC-NNN — Title`, labelled `spec` and its milestone (`M0`–`M8`).

```
PRD (wiki) ─► Spec (wiki, BR/AC/DL) ─► Issue + implementation plan (board)
   ─► branch ─► tests first for domain rules ─► code
   ─► commit (pre-commit: format + lint staged files)
   ─► push (pre-push: npm run check in each changed package, DV-37)
   ─► PR (template, rules cited) ─► CI gates ─► self-review ─► squash-merge
   ─► board updated, AC ticked ─► (deploy, once enabled)
```

An issue that adds a page or changes a page's layout also needs a **page frame approved by the product owner on the issue before the branch is cut** (DS-30); the PR links it.

| Stage              | Owner of the truth                          | What changes there                                     |
| ------------------ | ------------------------------------------- | ------------------------------------------------------ |
| Product decision   | PRD `D-nn`, `Questões-em-Aberto-e-Decisões` | A new decision or an answered question                 |
| Behaviour          | Spec `BR-NNN-nn`, `AC`, `DL-NNN-nn`         | A rule changes → the spec changes first, then the code |
| Plan and progress  | The spec's issue                            | Implementation plan, checklist, links to PRs           |
| Technical decision | ADR (§10)                                   | A choice the specs did not anticipate                  |
| How we build       | These guidelines                            | Through a PR like any other change                     |

|           |                                                                                                                                                                                        |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-21** | Code never silently disagrees with a spec. If implementation shows a rule is wrong, the spec is amended (with a Decision Log entry) in the same cycle, and the PR links the amendment. |
| **DV-22** | Domain rules are written test-first: the test states the rule with a hand-computed expectation (TS-04), then the code makes it pass.                                                   |
| **DV-23** | Work that is out of scope for the current PR becomes an issue on the board, not a `TODO` and not a silent expansion of the PR.                                                         |

## 8. Git and pull requests

**Trunk-based.** `main` is always releasable. Branches live a day or two and are squash-merged.

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-24** | Branch names: `feat/spec-011-office-invites`, `fix/spec-004-bom-header`, `chore/…`, `docs/…`, `refactor/…`. Include the spec id when one applies.                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **DV-25** | [Conventional Commits](https://www.conventionalcommits.org/): `feat(journeys): block writes on read-only offices`. The squash-merge title follows the same format.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **DV-26** | The commit/PR body names the rules implemented: `Implements SPEC-002 BR-002-30.` Breaking API, schema or config changes carry `BREAKING CHANGE:` in the footer.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **DV-27** | Every change goes through a PR — self-reviewed when solo. `main` is protected by a repository ruleset: PR required (0 approvals, since a solo author cannot approve their own PR), every required status check green (§12), branch up to date with `main` before merging, linear history, squash merge only, no force-push, no deletion, and no merge while CodeQL reports a new high or critical alert. The repository admin is the ruleset's only bypass actor, kept for emergencies (a broken check blocking a fix); a bypass is the exception, said in the PR, and never used by an agent. |
| **DV-28** | Never commit `.env` files, real personal data, production exports, or anything copied from a user's account (SC-32).                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

**Agent merge flow.** An agent never pushes to `main` and never merges with `--admin`. It opens the PR, waits with `gh pr checks <n> --required --watch`, and when the branch is behind `main` runs `gh pr update-branch <n>` and waits for the checks again (the branch must be up to date). It merges with `gh pr merge <n> --squash` only once every required check is green and the user has approved the merge; auto-merge stays off.

The PR template lives at [`.github/pull_request_template.md`](../../.github/pull_request_template.md). A PR:

- links the spec issue (`Closes #N` only when it completes the spec; otherwise `Part of #N`);
- lists the BR/AC it implements and ticks the AC it satisfies;
- says how it was verified;
- includes screenshots in light and dark, desktop and 360 px, for UI changes, and links the approved frame for a new or changed page (DS-30);
- updates the guidelines or `README`s it makes stale.

## 12. CI/CD

GitHub Actions, in [`.github/workflows/`](../../.github/workflows/). The repository is public, so minutes are not the constraint — the full suite runs on every PR and on `main`. CI does not filter by path; only the pre-push hook (DV-37) skips unchanged packages.

Every workflow pins each action to a full commit SHA with its version in a comment (`uses: actions/checkout@<sha> # v7.0.1`), declares least-privilege `permissions:` at the top level (a job widens only what it needs), never uses `pull_request_target` or `workflow_run`, checks out without persisting credentials, and takes Node from `.node-version` through `node-version-file` (SC-21, DV-05). The `structural` job enforces all of it, and the repository's Actions settings require SHA-pinned actions as well. Upgrading an action means changing the SHA and the comment together.

### `codeql.yml` — every PR, every push to `main`, weekly

| Job      | Steps                                                                                                                                                             | Blocking                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `codeql` | CodeQL advanced setup for JavaScript/TypeScript, `security-extended` queries, no build needed. The repository's CodeQL default setup stays off (the two conflict) | ✅ on high/critical — the ruleset's code-scanning rule blocks a merge on a new high or critical alert |

`concurrency` cancels a superseded run on a PR; runs on `main` always finish. `PUPPETEER_SKIP_DOWNLOAD` is set in CI: no job drives a browser, and npm 11 skips puppeteer's install script anyway.

**Required status checks on `main`** (DV-27), by check name (the job id, or the matrix job's `name`): `backend-static`, `backend-test`, `backend-integration`, `backend-build`, `frontend-static`, `frontend-test`, `frontend-build`, `backend-image`, `frontend-image`, `audit`, `structural`, `codeql`; `e2e` joins when #3 lands. Renaming a job means updating the ruleset in the same change.

### Hosting today

The production files are in [`deploy/`](../../deploy/): `compose.production.yml` (Caddy, frontend, backend and the `migrate` profile; only Caddy publishes ports), `Caddyfile`, `setup-server.sh` for the one-time server setup (an `admin` user with sudo and a `deploy` user with docker access only, both key-only), `close-ssh-login.sh` to close password and root SSH login afterwards, and the deploy job's `render-env.sh` (on the runner: the env files from the `deploy-production` environment), `release.sh` (server side: install the files, pull, migrate, replace, roll back) and `check-health.sh` (the health check from outside). Runtime configuration and secrets live in the `deploy-production` environment and reach the server as `/srv/farol/env/*.env`, written by every deploy and never edited there (DV-35, [ADR-004](../adr/004-production-configuration-from-github.md)); the API runs with `TRUST_PROXY_HOPS=1` behind Caddy. Staging is on hold (#103). The by-hand procedure, and how to turn the deploy job on, is [deploy-and-rollback.md](../runbooks/deploy-and-rollback.md).

Production runs on a Hostinger VPS in Brazil for both applications, with MongoDB on Atlas ([ADR-002](../adr/002-hosting-and-environments.md); BL-001, [#40](https://github.com/rafaelfqueiroz/farol-de-leiloes/issues/40)). Nothing else hosts the applications: Vercel and Railway are retired ([#116](https://github.com/rafaelfqueiroz/farol-de-leiloes/issues/116), ADR-002), so there are no per-PR preview deployments; staging (#103) is the later answer to that. The deploy job described below is the only path to production.

The environment is named `deploy-production` and not `Production`: while Vercel was connected it reported to a GitHub environment called `Production`, and environment names are case-insensitive, so the two would have collided. Vercel's and Railway's environments are deleted with their integrations, and the name stays so the deploy wiring and [ADR-004](../adr/004-production-configuration-from-github.md) do not churn.

### `deploy.yml` — images on every push, deploy behind `DEPLOY_ENABLED`

**The deploy job is built but off** until the owner sets `DEPLOY_ENABLED` ([ADR-002](../adr/002-hosting-and-environments.md), BL-001); the first deploy to a fresh server is a `workflow_dispatch` run of `deploy.yml` on `main`. The images are published on every push to `main` either way; the build itself is proven on every PR by `backend-image` and `frontend-image` in `ci.yml`:

```
build images (backend, frontend) ─► tag with commit SHA ─► push to GHCR
  ─► preflight: DEPLOY_ENABLED set?  ── no ─► skip quietly
                                      └─ yes, secrets or required values missing ─► fail loudly
  ─► deploy: render the env files ─► (SSH as `deploy`) install them with compose + Caddyfile
       ─► pull ─► run migrations (gated; failure stops, previous files put back)
       ─► replace the single backend ─► GET /api/health ─► roll back to the previous SHA on failure
```

- `images` builds both images from the same Dockerfiles as the PR check and pushes them to `ghcr.io/rafaelfqueiroz/farol-de-leiloes-{backend,frontend}:<full SHA>`, never `latest`; the packages are private, and the server pulls them with its own read-only token.
- `preflight` (only on `main`, in the `deploy-production` environment, `contents: read`) checks that the secrets `DEPLOY_HOST`, `DEPLOY_SSH_KEY` and `DEPLOY_KNOWN_HOSTS` and the variables `NEXT_PUBLIC_AUCTIONS_API_URL` and `NEXT_PUBLIC_SITE_URL` are set, and, through `deploy/render-env.sh check`, every runtime value production requires (the LLM key only for the selected `LLM_PROVIDER`), naming what is missing without printing any value.
- `deploy` (same environment, `contents: read`) renders `caddy.env`, `frontend.env` and `backend.env` from the environment's secrets and variables (`deploy/render-env.sh`, ADR-004) into a runner directory of mode 700, connects with plain OpenSSH and the pinned host key (never `ssh-keyscan` or `StrictHostKeyChecking=no`), copies this commit's `compose.production.yml` and `Caddyfile` and the env files to the server (over SSH, never on a command line), and sends `deploy/release.sh` over SSH, so the server never runs a stale copy. The script installs the files (the env files in `/srv/farol/env`, keeping the previous set to restore on a failed migration or a rollback), pulls, runs the `migrate` service (DV-34), recreates a container whose env file changed, replaces the single backend, starts frontend and Caddy, reloads Caddy and waits for the container's health check; the runner then checks `GET /api/health` and the site through Caddy (AR-48, `deploy/check-health.sh`). A failure after the backend was replaced rolls back to the previous SHA and its files, without migrations (DV-33, AR-28), and the job still fails. Each step has a timeout, and the key file and the rendered env files are removed at the end.

Runs never overlap: the workflow-level `concurrency` group queues them. A publishing workflow uses no npm or build cache. The runbook ([deploy-and-rollback.md](../runbooks/deploy-and-rollback.md)) has the full sequence, the files the job keeps in `/srv/farol`, and how to turn it on.

The images:

- `backend/Dockerfile` — multi-stage on `node:<.node-version>-slim`; the runtime stage holds the compiled `dist/` and production dependencies, runs as `node`, and installs Debian's `chromium` for the scraper (`PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium`; puppeteer's own download is skipped). bcrypt loads the prebuilt binding in its package, so no compiler is installed.
- `frontend/Dockerfile` — Next.js `output: 'standalone'`, runs `node server.js` as `node` on `PORT=3001`. The `NEXT_PUBLIC_*` values are inlined at build time, so `ci.yml` and `deploy.yml` pass them, to the frontend leg only, as build arguments from the repository variables `NEXT_PUBLIC_AUCTIONS_API_URL`, `NEXT_PUBLIC_SITE_URL` and `NEXT_PUBLIC_SENTRY_DSN` — public values only (SC-16). The backend Dockerfile declares no build arguments.
- Each package's `.dockerignore` keeps `.env*` out of the build context; runtime configuration and secrets come from the env files the deploy job delivers, never the image (SC-16, DV-35).

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **DV-33** | Images are tagged with the commit SHA. Rollback is redeploying a previous SHA, which only works because migrations are forward-only and expand/contract (AR-28).                                                                                                                                                                                                                                                                         |
| **DV-34** | Migrations (AR-29) run as a separate, gated step **before** the new code starts (`npm run migrate`, §6). A failed migration aborts the deploy and leaves the running version untouched. | **DV-36** | `DEPLOY_ENABLED` is a repository variable separate from the secrets: unset, a missing secret is expected and the deploy skips; set, a missing secret or required runtime value is a fault and `preflight` fails.                                                                                                                                                                                                                         |

### `nightly.yml`

Daily at 03:17 Brasília (and on demand): `npm audit` with the full advisory list, every severity and dev dependencies included, written to the run summary; the job fails only on a high or critical advisory, so the failed-run email is the alert for an advisory published against code nobody has pushed. ## 13. Definition of done

A spec's issue is closed when:

- [ ] Every acceptance criterion is ticked and demonstrable
- [ ] Every business rule is implemented, or explicitly deferred with a note in the spec
- [ ] `npm run check` passes and CI is green, including coverage gates
- [ ] Every new owned collection has `ownerType`/`ownerId` and its isolation spec (AR-11, AR-16, TS-14)
- [ ] Migrations reviewed, idempotent and expand/contract (AR-28, AR-29)
- [ ] No personal or client data in logs, errors or Sentry (SC-15)
- [ ] User-facing text in pt-BR through next-intl, with Caixa vocabulary (DS-20)
- [ ] Screens work at 360 px, in light and dark, by keyboard, and pass axe (DS-13, DS-21)
- [ ] New or re-laid-out pages match their approved frame (DS-30)
- [ ] Endpoints documented in OpenAPI (AR-33)
- [ ] LGPD data inventory updated for any new personal data field (SC-25)
- [ ] ADR written for any technical decision the specs did not cover
- [ ] Docs updated (DV-29)
