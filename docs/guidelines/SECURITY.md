The specs say **what** must hold; this document says **how the code makes it hold**. Rules are numbered `SC-nn`. Where a spec rule already says it, the guideline cites it rather than restating it.

## 1. What we protect, and from what

| Asset                                                         | Worst realistic failure                                                                               |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| An office's clients, journeys, costs and documents            | Another office — possibly a competitor — reads them, or learns the client exists (SPEC-002 BR-002-04) |
| Investor profiles and holdings                                | Financial position exposed to a stranger                                                              |
| Documents in R2 (matrículas, contracts, IDs)                  | A leaked or long-lived link                                                                           |
| Third parties in those documents (previous owners, occupants) | Profiling people who never signed up (SPEC-010 BR-010-25, PRD constraint)                             |
| Accounts and sessions                                         | Takeover through a stolen token or brute force                                                        |
| Payments state                                                | A forged, replayed or out-of-order webhook upgrading, or failing to lapse, an office's plan             |

## 2. Authentication

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SC-01** | Passwords are hashed with `bcrypt`, cost ≥ 10, never logged, emailed or returned (SPEC-001 BR-001-12). Length 8–128, no composition rules (BR-001-13).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **SC-02** | **The session token lives only in an `httpOnly`, `Secure`, `SameSite=Lax` cookie** set by the server. Never `localStorage`, `sessionStorage`, a URL or a JS-readable cookie. State-changing requests rely on `SameSite` plus an `Origin` check; a cross-site form cannot act. In the web app the Next.js route handlers (the BFF) set and read the cookie (`__Host-farol_session` in production, `farol_session` over plain-http development; 7 days, BR-001-18), build `Authorization: Bearer` for the backend from it and clear it only on an explicit sign-out (`POST /api/auth/logout`), never from a data request's `401 UNAUTHENTICATED`: the BFF is stateless and cannot know which cookie the browser holds when a slow answer returns, so a late 401 for an old session would wipe a newer sign-in (BR-001-18); the dead cookie is `httpOnly` and harmless (the backend refuses it, the next sign-in overwrites it) and the browser ignores 401s of requests that started before the session changed; a state-changing BFF request whose `Origin` (or `Sec-Fetch-Site: same-origin`, when `Origin` is absent) is not the site's own gets `403 FORBIDDEN` before anything else. Browser code never holds the token and never sets `Authorization`; `test/structural/session-token.test.ts` fails the build if it does. The backend still authenticates the Bearer header only. **Sign-in with Google is protected against login CSRF** (issue #152): the start route sets a short-lived (10 minutes) `httpOnly`, `SameSite=Lax`, `Secure` in production, `Path=/api/auth/google` cookie holding the OAuth `state` and the PKCE (S256) code verifier, HMAC-signed with a key HKDF-derived from `JWT_SECRET` (no new secret), and the callback is refused as `GOOGLE_SIGN_IN_FAILED`, before any token request, when the cookie is missing, altered or expired or the returned `state` is missing or different; the cookie is cleared on every callback and neither the state nor the verifier is ever logged or put in a URL (`GoogleOAuthStateStore`). |
| **SC-03** | A valid signature is not enough: every authenticated request checks the account's current status (deactivated, closed) and current memberships (SPEC-001 BR-001-16, SPEC-002 BR-002-15). The session is a server-side record keyed by the token's `jti` (`sessions`, 7 days): sign-out revokes it, a password change revokes the account's other sessions and a reset revokes all of them (BR-001-18, BR-001-19). A session is also bound to the credential it was issued for: it stores the account's `credentialVersion` as read from the document that proved the credential, and `JwtStrategy` refuses it once the account's version differs (missing counts as 0). Every password write bumps the version in the same atomic update as the hash, and change-password and set-password are fenced on the version their decision was based on (a competing change makes the write fail with `UNAUTHENTICATED`, nothing stored), so a sign-in that passed the password check just before a reset cannot keep a session opened after it, and a failed revocation write leaves nothing usable; the session that made the change is re-stamped and stays. Password sign-in only considers an account with the `local` provider and a stored hash (DL-001-02). A credential takeover (Google link of an unconfirmed account, DL-001-02) is itself such a write: it bumps the version in the same atomic update that deletes the password and removes `local`, so a change-password already past its password check cannot store the attacker's new password afterwards (its fenced write matches nothing) and a sign-in that passed the check just before cannot keep a session. The same atomic update starts a new consent generation (`users.consentResetAt`, and clears `whatsappPromptAnsweredAt`), so the acceptances and WhatsApp consent that whoever registered the address left behind never count as the owner's (SPEC-010, ARCHITECTURE §13).                                                                                                                                                                                                                                                                                                                                                                                 |
| **SC-04** | Sign-in, sign-up, password reset and confirmation resend are throttled. Sign-in attempts (and the current-password check of change-password) are counted per email and per origin in `loginAttempts` at the limits SPEC-001 BR-001-15 sets: the count is taken atomically _before_ the password is compared, so the 11th attempt in 15 minutes is refused with `TOO_MANY_ATTEMPTS` even with the right password and the ban runs 15 minutes from that refusal. The 15 minutes are a rolling window, `(now - 15 min, now]`: the row keeps the instants of the attempts inside it, so failures leave the count one by one and none is forgotten by a reset of the whole counter. The origin is `req.ip` normalised (IPv4-mapped to IPv4, IPv6 to its /64). It is the real client behind the BFF too: Caddy discards any client-sent `X-Forwarded-For` and appends the real peer, the BFF forwards that chain unchanged (each entry a valid IP address, at most 5, otherwise none; `frontend/lib/forwarded-for.ts`), and the backend trusts it by hop count only (`TRUST_PROXY_HOPS`, `app.setup.ts`): a leading entry a client injects is never read, and with 0 hops the header is ignored. No new header or secret exists, and the backend port stays unpublished, so nothing but the BFF and Caddy can reach it with a forged chain. Sign-up, recovery request, reset, resend and change-password also carry a coarse per-origin `@nestjs/throttler` limit (`TOO_MANY_REQUESTS`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **SC-05** | Responses never reveal whether an email has an account: same message and same timing on sign-in failure and reset request (BR-001-14).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **SC-06** | One-time tokens (email confirmation, password reset, invitation) are ≥ 32 random bytes from `crypto.randomBytes`, stored **hashed**, single-use, and expire (1 hour unless a spec says otherwise).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## 3. Authorization

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SC-07** | **Deny by default.** `JwtAuthGuard` is registered globally; a public endpoint opts out with `@Public()`, which a reviewer reads as a decision. An access requirement (`@AdminOnly`, `@RequiresPersona`, `@RequiresEntitlement`) always overrides `@Public()`, at handler or controller level: the route authenticates, and the access guards never pass a request without a user (`isPublicRoute`; a structural test rejects mixing the two on one handler or controller).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **SC-08** | Ownership and permission are enforced on the server on every request, through the scoped repositories and `AccessContext` of ARCHITECTURE §4 (AR-11–AR-16). Hiding a button is never the control (BR-002-10).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **SC-09** | Admin capability grants no client data and no paid feature (BR-002-23). It is `users.isAdmin`, read on every request (BR-002-15) and checked by `AdminGuard` (`@AdminOnly()`) on the platform-operation endpoints; the plan tier `role: 'admin'` grants nothing, and no guard lets an admin through a plan or persona check. `@AdminOnly()` also requires a confirmed email (`EMAIL_VERIFICATION_REQUIRED`, BR-001-04 semantics), against a pre-registration takeover of a colleague's address. No API writes the flag: only the ops script `npm run grant-admin`, which refuses an office member, an investor or a self-advised account (BR-002-21, DL-002-05), and an account whose email is unconfirmed (`refused_unconfirmed_email`) or that is not active (`refused_inactive`); its grant write is conditional on the state it checked. The only path from an admin to client data is a **support access grant** (BR-002-24–BR-002-27, ARCHITECTURE §4): opened only on an open support request whose requester allowed data access (anything else answers like a nonexistent request), bound to one admin, re-checked on every read against the current request and the clock (closed, withdrawn or 7 days → refused), read-only and never wider than the requester's own current view, and every record read is logged in the insert-only `adminAccessLogs` before it is returned — a log that cannot be written refuses the read. A grant opens **client data only**, never the requester's own favorites, saved filters or reminders (BR-002-02, BR-002-23: `AccountScopedRepository` refuses the grant's view), and the view is sealed so that only `GrantReadLogger` reads with it (BR-002-27). **Append-only in the database (owner action, BR-002-27):** the repository, the schema middleware and `test/structural/admin-access-append-only.spec.ts` (which refuses any lookup of the two models or collections outside `admin-access/`, however spelled) bind our code, not the database. The real control is the API's MongoDB user: an Atlas custom role granting, on `adminAccessLogs`, only `find`, `insert`, `createCollection` and `createIndex` (the last two for migration 0005, which runs as the same user) — no `update`, `remove`, `dropCollection`, `dropIndex`, `collMod` or `renameCollectionSameDB` — and on `supportAccessGrants` the same plus `update` (the end transition), never `remove` or a drop. Privileges add up, so the role must not also hold database-wide `readWrite` (it would include both collections): the other collections get their actions per collection. Until the owner sets it on Atlas, the API user's broader role leaves append-only to the code checks. There is no "admin bypass" flag on scoped repositories, and no production grant route exists until SPEC-009 (the support request source knows no request until then). |

## 4. Input and output

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **SC-10** | Every input is a validated DTO (AR-34). Request values never become MongoDB operators: no spreading `req.query`/`req.body` into a filter, `sanitizeFilter: true` and `strictQuery: 'throw'` on the connection, and any free-form sort/filter field is checked against an allowlist. `sanitizeFilter` and `strictQuery` are switched on by `applyMongooseDefaults()` (`backend/src/common/mongo/query-safety.ts`) before the first query; unknown schema paths must throw, including inside `$or`, rather than being stripped and widening reads or writes (AR-12). A scalar taken from a request is compared as `{ field: { $eq: value } }` after a `typeof` check, and operators the server writes itself (`$in`, `$gte`, `$exists` ...) are wrapped in `serverOperators(...)`, never a value that came from a request. An update is built from whitelisted fields under `$set`, never from the DTO object. |
| **SC-11** | The Stripe webhook verifies the signature against the **raw** body, is idempotent by event id, and is the only path that changes plan state (SPEC-012 BR-012-09, BR-012-14: no user endpoint sets a plan, a subscription state or a limit, and the checkout redirect never upgrades anything). **Idempotent by event id**: `paymentEvents` is inserted by the provider event id (unique index); a repeat of a processed event is acknowledged and does nothing, a repeat of one never marked processed (a crash or fault midway) is handled again, and `processedAt` is set only after it was handled in full. **The payload is not trusted for state** (BR-012-13): an event is only a pointer to a subscription; the service takes that record's sync lease (one conditional update), re-reads the subscription from the provider **inside** the lease and writes what it says, conditional on still holding the lease, so a duplicate, late or out-of-order event cannot overwrite a newer state. A delivery that finds the lease taken leaves a conditional re-sync request that the holder reads atomically with its release and answers success, so a burst is coalesced into reads that follow the last event (no delayed 503; `WEBHOOK_BUSY` only after bounded attempts, and the provider retries). After a sync the record equals what the provider said at that read; a record can lag the provider until the next event or read (lost events are healed by the daily reconcile job, which re-reads every non-lapsed subscription through the same lease path). **The same event delivered twice at the same moment** runs the handler once: the ledger document carries a processing claim (token and expiry, one conditional update), the loser answers `WEBHOOK_BUSY` and its retry finds the event processed. Only a signature failure is a 400; a failure to map a verified event is a 5xx fault; an event of the other mode than the key (test vs live) is ignored. A subscription that carries our ref but has no record, or does not match its record, is a fault, never an acknowledgement. Our records hold no amounts, and card data never reaches us (BR-012-10). The signature failure is logged by its code only. Two subscriptions in effect for one office are resolved by the provider's state (the conflicting one is read again first); if both are in effect, the one paid later is cancelled at the provider (idempotently), never an older paid one in favour of a late reactivation (BR-012-08). **The office billing routes** (`/api/office/subscription`, SPEC-012 BR-012-11) are an owner surface: the office is always `ctx.resolveActingOwner(officeId?)` among the caller's CURRENT memberships (never a path id; a non-member, a removed member and an unknown id get the same `NOT_FOUND`), the success page's `GET /api/subscriptions/checkout/:ref/status` is authorised by `buyerUserId == ctx.accountId`, bodies are whitelisted DTOs (a request naming a status, plan, limit or owner is a `VALIDATION_FAILED`), every provider mutation carries an idempotency key, and no route changes a stored status: each asks the provider and re-reads it. **The refund** (BR-012-29) is every payment the first subscription received (each paid invoice minus what was already refunded, unpaid ones voided), claimed with one conditional update (`refundClaimedAt`, retakeable after 5 minutes, only for a subscription in effect and not yet refunded; a member who finds a live claim gets `CANCEL_IN_PROGRESS`) and made per invoice with the stable provider key `refund:<ref>:<invoiceId>`; an idempotency or already-refunded error counts as done only after the provider's refunded amount is read back, a refund that returns less than was paid records and cancels nothing, and a failure before the refund is confirmed gives the claim back, so two members cancelling at once, a retry and a crash anywhere move the money once and a retry after the window of a request made inside it still completes. The success page and the reconcile job ask the provider about a checkout whose events never arrived and never delete a record unless the session is confirmed expired. The catalog script checks each price at the provider (amount, interval, BRL, active) before writing, so the plans page never shows what the provider does not charge. **Provider settings that are part of the control**: the Billing Portal restricted to the payment method and invoices (a plan change or cancellation made there would bypass BR-012-17, BR-012-19 and BR-012-29; in production the portal route fails closed, `BILLING_PORTAL_FAILED`, until `STRIPE_BILLING_PORTAL_CONFIGURATION_ID` is set, SC-16), and dunning that ends in cancel (the reconcile job assumes it). The billing routes are throttled per account (SC-04) because each can reach the provider. Details: ARCHITECTURE §13, [ADR-005](../adr/005-office-subscriptions-on-stripe.md), [Stripe billing runbook](../runbooks/stripe-billing.md). |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **SC-12** | CSV exports neutralise formula prefixes (`=`, `+`, `-`, `@`) even after leading whitespace, and leading tab, carriage return or newline (formula injection). Use `neutralizeCsvCell` (`backend/src/common/exports/csv-cell.ts`) on each untrusted text cell before CSV quoting. XLSX exports instead create explicit string cells and never set formula properties from untrusted input; CSV apostrophe prefixes would be visible text there. These boundaries are ready for SPEC-010 exports.                                                                                                                                                                                                                                                                                                                                                                                                               |
| **SC-13** | Uploads (SPEC-017) go straight to R2 through a presigned URL scoped to one key, with an allowlist of content types, a size cap, and the type re-checked from the stored object's bytes before it is marked usable. Files are never served from the application origin.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **SC-14** | The server never fetches a URL a user supplied. Outbound requests go only to configured hosts (Caixa, Stripe, OpenAI, R2, mail/SMS providers).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

## 5. Data protection in the running system

|           |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SC-15** | **No personal or client data in logs, error messages, Sentry, analytics or job records** — no names, emails, phones, CPFs, journey content, figures, profiles or support messages (SPEC-002 BR-002-28). Ids, codes and counts only; a user appears as a hashed id (AR-46, AR-47).                                                                                                                                                                                                                                                                             |
| **SC-16** | Secrets come from the environment only, are validated at boot (AR-41), never logged, never committed, never baked into an image (each package's `.dockerignore` excludes `.env*`), never sent to the browser. A `NEXT_PUBLIC_` variable is public by definition and never holds a secret.                                                                                                                                                                                                                                                                     |
| **SC-17** | Transport and headers: HTTPS only with host-only HSTS (`max-age=15552000`, six months; no `includeSubDomains` or preload until a separate audited decision); `helmet` on the API; on the web, an explicit Content-Security-Policy (no `unsafe-eval`; `unsafe-inline` only where MUI's style injection needs it, with a nonce when available), `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`. CORS is an explicit allowlist, never `*` with credentials. No `dangerouslySetInnerHTML` with anything not sanitised.              |
| **SC-18** | R2 buckets are private. Download links are issued per request after an authorization check and expire in 60 seconds (BR-002-09); they are never stored, emailed or logged. Object keys are random and carry no personal data. Client files live under `private/` in their own bucket, `R2_PRIVATE_BUCKET`, which has **no public access** and is never `R2_BUCKET` (served openly at `R2_PUBLIC_URL`; the API refuses to boot when they are equal). They are linked only by `StorageService.issuePrivateFileLink(key)` (60 s fixed, `PRIVATE_FILE_LINK_SECONDS`; signs against the private bucket only and refuses when it is unset, never falling back to the public one; refuses any other key; no public URL; neither key nor link logged, and the other storage operations log a private key as `[private file]`); `getSignedUrl` refuses private keys. The owner creates the private bucket and sets `R2_PRIVATE_BUCKET` before SPEC-017 ships. |

The baseline in #37 registers `JwtAuthGuard` globally in `AuthModule`; only `@Public()` metadata skips JWT authentication, and never on a route with an access requirement (SC-07). `configureApp` adds Helmet, while its CORS allowlist contains only the validated, normalized `FRONTEND_URL` HTTP(S) origin (SC-17). The frontend config declares security headers and its proxy supplies a fresh CSP nonce to Next.js and MUI on each HTML request; production enforces CSP and development reports violations without allowing `unsafe-eval`. See both package READMEs for operation and cache details.
