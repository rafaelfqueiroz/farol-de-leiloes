Auctions API (NestJS 12 + MongoDB)

Overview

- Ingests daily CSVs from Caixa auctions (per state, option "Todos").
- Parses and normalizes fields, stores in MongoDB.
- Exposes REST endpoint to query by state, city, and modality.

Requirements

- Node.js 24.22.2 (pinned in `.node-version`; DV-05)
- MongoDB running locally or a connection string (to run the app)
- Docker running, for `test:integration` and `test:isolation` (Testcontainers starts MongoDB; DV-17)
- Chrome for the detail-page scraper: npm 11 does not run puppeteer's install script, so run `npx puppeteer browsers install chrome` once (production images install Chrome/Chromium explicitly; ARCHITECTURE §13)

Setup

1. Copy `.env.example` to `.env` and fill in every value: each secret and integration variable is required, and the API refuses to boot naming any that is missing or invalid (AR-41). Optional ones are marked in the file.
2. Install deps: `npm install`, and once at the repository root run `npm install` too to install the git hooks (husky + lint-staged)
3. Dev run: `npm run start:dev` — `tsc --watch` plus `node --watch` on the compiled `dist/`; the backend is native ESM, so relative imports end in `.js` (DEVELOPMENT §1 and §6)
4. Build: `npm run build`, then `npm start`. The deploy image is `Dockerfile` (Debian Chromium for the scraper, non-root), built and pushed to GHCR by `deploy.yml` (DEVELOPMENT §12)
5. Before pushing: `npm run check` (typecheck + lint + format check + tests); the pre-push hook runs it when `backend/` changes (DV-37)

Migrations (AR-29, ADR-001)

- `npm run migrate` — after `npm run build`: applies the pending migrations in `src/migrations/registry.ts` to the database `MONGODB_URI` names (same validated environment as the API), records each in the `migrations` collection and stops at the first failure (exit 1). Safe to re-run. It runs **before** deploying code that depends on it (DV-34); until the deploy pipeline does it (BL-001, #40), run it by hand from your machine against the production database (MongoDB Atlas) first, with `node --env-file=.env.production dist/migrations/run.js` (see DEVELOPMENT §6). How to write one: DEVELOPMENT §6, "Migrations"
- Migration `0005-admin-access-indexes` builds the indexes of `supportAccessGrants` (the partial unique `one_open_grant_per_request`, on which concurrent grant opens rely, BR-002-24) and `adminAccessLogs`; it is idempotent and only creates indexes (and the empty collections), so the API never depends on Mongoose's autoIndex for them.

Admin capability (SPEC-002 DL-002-05, BR-002-21)

- `npm run grant-admin -- --email <address>` gives the admin capability (`users.isAdmin`) to one account, `--revoke` takes it away. Like `migrate`, it runs from the compiled output (`npm run build` first) with the API's validated environment against the database `MONGODB_URI` names, so it also runs inside the production image (`node dist/access/grant-admin/run.js`). It refuses an account that is an office member, a client of an office (active or ended link), the investor of a journey or self-advised (BR-002-21), and one whose email is not confirmed or that is deactivated or closed (SC-09). It prints only the outcome (`granted`, `revoked`, `unchanged`, `account_not_found`, `account_changed`, `refused_client_relationships`, `refused_unconfirmed_email`, `refused_inactive`), never the address or account data (SC-15). Exit code 0 when the account ends up as asked. `account_changed` means the account changed between the read and the conditional write: run it again. `--revoke` also resets a legacy `role: 'admin'` to `'free'`, so a re-run of migration 0004 cannot grant it back. No API writes the flag, and `@AdminOnly()` refuses an admin whose email is not confirmed.
- Migration `0004-admin-capability` set `isAdmin: true` on every account whose `role` was `'admin'` (and `false` where absent); run it before deploying this code, or existing admins lose the admin screens until it runs.

Plans and subscriptions (SPEC-012, ARCHITECTURE §13, ADR-005)

- `npm run plans:upsert -- --file <catalog.json>` writes the plan catalog (`plans`) from the compiled output (`npm run build` first), with the API's validated environment, like `grant-admin`: `{ "plans": [{ "code", "name", "price": "199.90", "interval": "month" | "year", "activeJourneyLimit", "stripePriceId", "status"?: "OFFERED" | "WITHDRAWN", "sortOrder"? }] }`. The whole file is validated before anything is written, an upsert is idempotent by `code`, a provider price that belongs to another plan and a changed price id for an existing code are refused (a new price is a new code; withdraw the old one), and so is a price that does not exist at Stripe, is archived (for an offered plan) or differs in amount, interval or BRL (`refused_price_mismatch`: it needs the API's Stripe key); it writes the changed plans as one `bulkWrite` (re-run the same file after a crash) and prints counts only. Existing subscriptions keep the limit they copied (BR-012-04). Exit code 0 when applied.
- `GET /api/plans` is public, cached for 30 s (`Cache-Control: public, max-age=30`), throttled per origin, and answers the offered plans as `{ items }`. The only payments route is the Stripe webhook (`POST /api/payments/webhook`), the one path that changes a subscription (BR-012-14); it listens to `checkout.session.completed`, `checkout.session.expired`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid` and `invoice.payment_failed`. Create the Stripe Prices and upsert the catalog before checkout opens.
- `SUBSCRIPTION_GRACE_DAYS` (default 10) and `REFUND_WINDOW_DAYS` (default 7) are optional business settings (`.env.example`). `STRIPE_STANDARD_PRICE_ID` is gone: price ids live in the catalog.
- Office billing, for any current member of the office, also while it is read-only (BR-012-11, BR-012-28), all behind `ConfirmedEmailGuard`: `GET /api/office/subscription` (plan, status, limit, journeys in progress, period, scheduled change, lapse and read-only dates, refund eligibility, billing history), `POST /api/office/subscription/checkout | change | cancel | undo-cancel | billing-portal` and `GET /api/subscriptions/checkout/:ref/status` (`PENDING` / `CONFIRMED` for the success page). The office is the one the caller's memberships give (an optional `officeId` only chooses among them; anything else is the same 404). Cancelling the office's FIRST subscription inside `REFUND_WINDOW_DAYS` of its first confirmed payment refunds it in full and ends it at once; otherwise renewal stops and the plan runs to the period end. Interactive docs: `/api/docs`.
- `JourneySlotsService` (exported by `SubscriptionsModule`) is what SPEC-016 calls: `ensureCounter`, `reserve`, `release`, `inProgress` over the counter `journeys.active`; a refusal is `JOURNEY_LIMIT_REACHED { inProgress, limit }`.
- The daily reconcile job (`SubscriptionsReconcileJob`, 03:30 Brasília time) re-reads subscriptions from Stripe; `SUBSCRIPTIONS_RECONCILE_ENABLED=false` switches it off. `STRIPE_BILLING_PORTAL_CONFIGURATION_ID` (optional) names the restricted Billing Portal configuration. Both are in `.env.example`, `deploy/render-env.sh` and `deploy.yml`. Stripe setup (dunning, portal, webhook, reconcile): [docs/runbooks/stripe-billing.md](../docs/runbooks/stripe-billing.md).
- Migration `0007-billing-indexes` builds the open-checkout guard (`one_open_checkout_per_key`), the reconcile and purge reads on `subscriptions`, and the unique `ownerCounters` index; run it before deploying this code (DV-34).
- Migration `0006-subscription-indexes` builds the indexes of `plans`, `subscriptions` (the partial unique one that keeps a single subscription in effect per office, BR-012-08) and `paymentEvents` (unique event id, SC-11); run it before deploying this code (DV-34). `users.role`, `subscriptionStatus` and the Stripe ids are no longer written; their removal is a later contract step (AR-28).

API

- The reference is the OpenAPI document (AR-33): Swagger UI at `/api/docs` and the JSON at `/api/docs-json` on a running API, outside production only. There is no hand-written route table; the controller and DTO decorators are the source, and `src/openapi.spec.ts` holds them to the contract.
- Errors answer `{ code, context }` (AR-38). Lists take `page` and `pageSize` (max 100) and answer `{ items, total, page, pageSize }` (AR-35).
- Money is a string of reais over JSON, both ways (AR-17): `"1234.56"` — a dot, at most two decimals, no thousands separator. Responses round once to two places, half-even (AR-19). Coupon discounts are reais too (they were integer centavos before #34). In MongoDB money is `Decimal128` only: migration `0001-money-decimal128` converted the documents written before #34, and a reader refuses any other shape.

Security baseline (SC-07, SC-10, SC-12, SC-16, SC-17)

- Authentication is global through `AuthModule`'s `JwtAuthGuard`. A new endpoint requires a JWT automatically; anonymous endpoints must declare `@Public()` on their method or controller. Keep `@ApiJwtAuth()` on protected endpoints for the OpenAPI contract.
- Access (SPEC-002, ARCHITECTURE §4). Right after `JwtAuthGuard`, the global `AccessContextGuard` builds the request's `AccessContext` (`src/access/`) from the account's current relationships, read on every request from the SPEC-011/012/016 seams (`MEMBERSHIP_SOURCE`, `CLIENT_LINK_SOURCE`, `SELF_ADVISED_SOURCE`, `OFFICE_PLAN_SOURCE`; until those specs bind theirs, the defaults grant nothing). Handlers read it with `@Access()`. Routes opt into `@RequiresPersona(...)` (`PERSONA_REQUIRED`, 403), `@RequiresEntitlement(name, { write })` (`PLAN_NOT_ALLOWED`, or `OFFICE_READ_ONLY` for a write by a read-only office) and `@AdminOnly()` (`users.isAdmin`, `FORBIDDEN`). The legacy plan tier `role: 'admin'` grants nothing: admins get no paid feature (BR-002-23). `GET /api/auth/me` adds `isAdmin` and `personas`. Google OAuth still runs its own Google guard; the public Stripe webhook still verifies its signature.
- Accounts and sessions (SPEC-001 BR-001-12–BR-001-24, SC-01–SC-06). The token is a JWT carrying only `sub` (the account) and `jti` (the session); no email, name, role or plan (BR-001-17). The `jti` is the `_id` of a row in `sessions` (7 days, TTL index): `JwtStrategy` refuses a token whose session is missing, revoked, expired or another account's, and one whose account `status` is not `active` (BR-001-16, SC-03). A session also stores the account's `credentialVersion` (a counter on `users`, a missing one counts as 0) as it was on the document that proved the credential, and is refused once the account's version has moved on (DL-001-02, below). Role (the plan tier), plan and the admin capability are read from the database on every request. `POST /api/auth/logout` revokes the session at once; changing a password (and adding one to a Google-only account) revokes the account's other sessions and resetting it revokes all of them (BR-001-18, BR-001-19). Tokens issued before sessions existed have no `jti` and are refused: **every user signs in again once after this deploy**.
- One-time links (email confirmation 24 h, account recovery 1 h, the Google exchange code 60 s and the Google signup code 15 min) live in `accountTokens`: 32 bytes from `crypto.randomBytes`, only the SHA-256 stored, spent with one atomic update, and a new token of the same user and purpose deletes the earlier unused ones, also under concurrent requests (exactly one link stays valid), and a confirmation link is bound to the address it was mailed to, so it only ever confirms that address (the email itself is immutable, BR-001-26; BR-001-05, BR-001-22, BR-001-23). The lifetimes are in `src/auth/tokens/account-token-purposes.ts`. Password recovery always answers 200 and mails only when an account exists (BR-001-21).
- Google sign-in (SPEC-001 BR-001-08–BR-001-11, BR-001-20; terms recording is SPEC-010, #10). `GoogleStrategy` only turns Google's profile into a `GoogleIdentity` (`src/auth/google/google-identity.ts`); the rules live in `AuthService`. Google must report the email as verified (`_json.email_verified` and `emails[0].verified`; only boolean `true` or the string `'true'` counts, and when both are present both must agree), otherwise the sign-in is refused with `GOOGLE_EMAIL_NOT_VERIFIED`. The account is found by Google's permanent id first and only then by email (BR-001-11), so a changed Google email never moves the link; an account that is `deactivated` or `closed`, or whose email is linked to another Google id, is refused (`GOOGLE_SIGN_IN_FAILED`). Linking an existing account is `UsersService.linkGoogleIdentity`, one conditional pipeline update (the decision is inside the update, not read-then-write; the table is `src/users/domain/google-link.ts`): a confirmed account keeps its password and local provider; an unconfirmed one is confirmed, loses its password and the `local` provider, and the same update bumps its `credentialVersion`, which by itself refuses every session issued for the old credential, including one that a sign-in opens after the link because it had passed the password check before it (a credential takeover cannot be outrun by a racing login). `AuthService` then also revokes all its sessions and outstanding account tokens (pre-hijacking, DL-001-02); both clean-up steps are idempotent and attempted even if one fails, and a failure there leaves no usable session because the version already refuses them. Linking a confirmed account does not touch the version, so its open sessions keep working. Nothing is created for an email with no account until the terms are accepted (BR-001-09): the callback stores the verified profile (Google id, email, name) in `accountTokens` as a `google_signup` token for 15 minutes.
- The Google flow carries OAuth `state` and PKCE (S256), so a callback the browser did not start is refused (login CSRF, issue #152, SC-02). The API keeps no browser session, so `GoogleOAuthStateStore` (`src/auth/google/`, the `store` of `GoogleStrategy`, with `pkce: true`) keeps them in a cookie: `GET /api/auth/google` sends Google a random 32-byte base64url `state` and the PKCE challenge, and sets `farol_google_flow`, `HttpOnly`, `SameSite=Lax` (the callback is a top-level GET navigation from Google, which Lax cookies accompany), `Secure` when `NODE_ENV` is `production`, `Path=/api/auth/google`, 10 minutes. Its value is `<base64url JSON {state, verifier, expiresAt}>.<HMAC-SHA256>`, signed with a key derived by HKDF from `JWT_SECRET` under the label `google-oauth-state` (no new environment variable; a changed secret simply invalidates flows in progress). `GET /api/auth/google/callback` goes on only when the cookie is present, unaltered and unexpired (the `Clock`) and the `state` Google returned equals the cookie's (constant-time compare); it then hands the verifier to the token request and always clears the cookie. A missing, different, tampered or expired state, or no cookie, is refused as `GOOGLE_SIGN_IN_FAILED` (`/login?error=GOOGLE_SIGN_IN_FAILED`) before Google is asked for anything; the state, the verifier and the cookie are never in a URL, a message or a log. Starting a second flow in another tab replaces the cookie, so the first tab's return is refused and the person signs in again. The cookie is read with a small pure parser (`cookie-header.ts`) rather than a cookie dependency.
- The return from Google never carries a credential (BR-001-20). `GET /api/auth/google/callback` redirects to `{FRONTEND_URL}/auth/callback?code=<one-time code>` or, on a refusal, to `{FRONTEND_URL}/login?error=<ERROR_CODE>` (the code only; `GoogleCallbackRedirectFilter`). The frontend calls `POST /api/auth/google/exchange {code}`: for an existing account (a `google_exchange` code, 60 s, spent atomically) it answers `{ status: 'signed_in', accessToken, user }` like a login; for a person with no account yet (a `google_signup` code, not spent) it answers `{ status: 'terms_required', email, name }`. `POST /api/auth/google/complete {code, acceptTerms: true}` spends the signup code, creates the account (`UsersService.createGoogleAccount`: Google only, email confirmed, no password, searcher defaults) and opens a session; `POST /api/auth/google/cancel {code}` deletes the unused code and the profile in it, so declining stores nothing (SPEC-010 BR-010-01). An unknown, used or expired code is `INVALID_GOOGLE_CODE` (400). The three routes are throttled like the other public auth routes. The frontend's `/auth/callback` shows the terms screen between the two ("Falta pouco": accept and `complete`, or "Cancelar" and `cancel`); recording the acceptance (versions, time, method) is SPEC-010 (#10).
- Sign-in answers `INVALID_CREDENTIALS` alike for an unknown email, a wrong password and a deactivated or closed account, and always spends exactly one bcrypt comparison (BR-001-14). Each attempt is counted, atomically, before the password is compared, so parallel guesses cannot all reach bcrypt: the 11th attempt in 15 minutes for the same email or the same origin answers `TOO_MANY_ATTEMPTS` (429) even with the right password, and the ban runs 15 minutes from that refusal (refused attempts are not counted, so hammering does not extend it). The 15 minutes are a **rolling window**, not a counter that resets as a whole: a `loginAttempts` row holds the instants of the attempts inside the half-open interval `(now - 15 min, now]` (`attempts`, newest `limit + 1` at most, one aggregation-pipeline update per key), `count` is how many there are, and an attempt exactly 15:00 old no longer counts, so one failure at minute 0, nine at minute 14 and one at minute 16 leave ten inside the window at minute 16 and the next attempt is refused. A failed password keeps its attempt; a success clears the email's row and removes only its own reservation (the instant `reserve` returned) from the origin's. The collection is new in this PR, so the `attempts` field needs no migration. The origin key is `req.ip` with IPv4-mapped IPv6 reduced to IPv4 and IPv6 bucketed by its /64 (`src/auth/login-attempts/origin-key.ts`). `loginAttempts` expires on its own (BR-001-15): a row's `expiresAt` is the later of its latest attempt plus 15 minutes and the end of its ban (TTL index). The current-password check of `POST /auth/change-password` uses the same counters. `@nestjs/throttler` adds a coarse 20-requests-per-15-minutes limit per origin and route on sign-up, resend, recovery request, reset and change-password, answering `TOO_MANY_REQUESTS` (SC-04); it is off under `NODE_ENV=test`. The origin is `req.ip`, the real client on both paths through `TRUST_PROXY_HOPS`: directly behind Caddy (the Google start and callback) and behind the BFF, which forwards Caddy's `X-Forwarded-For` chain unchanged and is the first trusted hop. A leading entry a client injects is never read, and with 0 hops the header is ignored (`test/integration/auth-origin-behind-bff.spec.ts`).
- Credential version (DL-001-02, BR-001-19, BR-001-28, SC-03). `users.credentialVersion` (number, default 0, server-written only) counts the credential changes of an account; `sessions.credentialVersion` is the version the session was issued for, and `JwtStrategy` refuses a session whose version differs from the account's (a missing one is 0 on both sides). `AuthService.startSession(user)` stamps `credentialVersionOf(user)` (`src/users/domain/credential-version.ts`), and `user` is always the document that proved the credential (the one `validatePassword` returned), never a later fetch: a sign-in that passed the bcrypt comparison before a password reset completed therefore opens a session carrying the old version, which the next request refuses, even though the reset's `revokeAllForUser` ran before that session existed. Every password write moves the version by one in the SAME atomic update as the hash (`$inc`): recovery (`setPassword` after the spent token) unconditionally, and still revokes every session; the Google takeover of an unconfirmed account (`linkGoogleIdentity`) bumps it in its own pipeline update, which also deletes the hash and removes `local`; change-password and set-password are fenced, i.e. the update predicate includes the version read when the current password was verified (change-password) or when "no local provider" was checked (set-password), and when a competing change moved it first nothing is written and the answer is `UNAUTHENTICATED` (401). After a successful change or set-password the current session is re-stamped with the new version (`SessionsService.rebind`) so the caller stays signed in, and every other session is revoked (and, carrying the old version, refused even if that revocation failed). `validatePassword` only finds an account with `local` among its providers AND a stored hash, so an account that lost `local` can never sign in by password even if a hash is left in the document; it still spends exactly one bcrypt comparison. The consequence for an in-flight `POST /auth/change-password` that verified the old password just before a Google takeover: its write is fenced on the version it verified (and on `local`), the takeover moved the version, so the write matches nothing and answers `UNAUTHENTICATED` (401); the attacker's new password is never stored (`test/integration/auth-credential-fence.spec.ts`).
- The profile is a closed allowlist (BR-001-25, BR-001-29, BR-001-31, RNF-13). `PATCH /api/auth/profile` accepts `name` (trimmed, 1–120 characters), `phone` and `email`; any other property is refused as a whole with `VALIDATION_FAILED`, and nothing is written. `UsersService.updateProfile` copies exactly `name` and `phone` into an explicit `$set`/`$unset`. The email is read-only for everyone (BR-001-26, D-63): `email` is accepted only when it equals the current address (a no-op, because the profile page still sends it) and any other address answers `EMAIL_CHANGE_UNAVAILABLE` (409). The phone is a Brazilian number with area code in a common format (`(84) 99999-1234`, `84999991234`, `+55 84 99999-1234`, `(84) 3222-1234`), validated against the real DDD list in `src/users/domain/phone.ts` and stored as E.164 (`+5584999991234`); an empty string or `null` removes it. The legacy `PATCH /auth/profile/complete` is gone, and the profile (`UserProfileResponseDto`, from `login`, `GET /auth/profile/full` and the rest) no longer returns `cpf`, `dateOfBirth`, `sex` or `address`: the users schema keeps those four fields so stored data stays untouched, and nothing reads or writes them until SPEC-010 decides their fate (BR-010-06, SC-26); `test/support/profile-fields.ts` classifies them as `LEGACY_UNUSED` and the schema-walk specs prove no write path reaches them. `UsersService.update` is internal (payments) and no controller binds `UpdateUserDto`, `CreateUserDto` or an entity as a body (`test/structural/controller-body-types.spec.ts`). `test/support/profile-fields.ts` classifies every path of the user schema; a new field fails the schema-walk specs until someone decides whether it may be written.
- An account whose email is not confirmed can sign in, edit its profile and ask for a new link, but `ConfirmedEmailGuard` (opt-in with `@UseGuards(ConfirmedEmailGuard)`) refuses it on the favorites, saved-filters, reminders and support controllers with `EMAIL_VERIFICATION_REQUIRED` (403) (BR-001-04). It reads `emailVerified` from the database on every request, so confirming takes effect on the same session; a `@Public()` handler stays public. Confirmation and recovery emails are account notifications and are always sent (BR-001-07). Note for the frontend: `GET /api/favorites/codes` (the heart state) is now 403 for an unconfirmed account too, handled by the global confirm-your-email banner.
- Sign-up takes exactly `email`, `name`, `password` (8–128 characters, no composition rules) and `acceptTerms` (required, must be `true`: a missing or `false` value is `VALIDATION_FAILED` and creates no account; recording it is SPEC-010, #10); anything else is refused as a whole (BR-001-02, BR-001-13, BR-001-31). Emails are trimmed and lower-cased on the way in and on every lookup (BR-001-01).
- `configureApp` applies Helmet to all API responses, including errors: HSTS, framing denied, `nosniff`, and `strict-origin-when-cross-origin`. HSTS is an explicit six-month policy for the serving host only (`max-age=15552000`), with no `includeSubDomains` or preload commitment; subdomains have not been audited. The nonproduction Swagger UI uses same-origin external scripts under the same CSP, without `upgrade-insecure-requests` so HTTP localhost/LAN access works. Production retains that upgrade directive and must be served behind HTTPS.
- CORS credentials are allowed only for the exact `FRONTEND_URL` origin. Its boot validation accepts HTTP(S) origins, rejecting credentials, wildcard hosts, paths, queries and fragments, and normalizes a permitted trailing slash away through `URL.origin` for every consumer (OAuth, email, Stripe and CORS). A different frontend origin requires an explicit configuration change.
- Mongoose enables `sanitizeFilter: true` and `strictQuery: 'throw'` before the first query. Keep query fields explicitly allowlisted in DTOs and builders, sorts fixed by the server, and trusted server operators behind `serverOperators`; unknown schema paths throw instead of disappearing and widening read/write predicates, including inside `$or`.
- Future SPEC-010 CSV exports must call `neutralizeCsvCell` (`src/common/exports/csv-cell.ts`) on every untrusted text cell before serialization. It prefixes an apostrophe for formula prefixes (`=`, `+`, `-`, `@`) even after leading whitespace, and for leading tab, carriage return or newline; it preserves the original whitespace, and the serializer must still quote CSV delimiters and quotes. XLSX exports must use explicit string cells and never set formula properties from untrusted text; do not apply CSV apostrophe escaping to XLSX, where the apostrophe would display literally.
- Secrets remain server-side and are never logged; the frontend's explicitly allowed public environment values contain no secrets (SC-16).
- Client files (SPEC-017) live in a separate R2 bucket, `R2_PRIVATE_BUCKET`, with no public access, never in `R2_BUCKET`, which `R2_PUBLIC_URL` serves openly; the API refuses to boot when the two are equal (SC-18, BR-002-08). The variable is optional until SPEC-017: while it is unset, `StorageService.issuePrivateFileLink` and any upload, download or delete of a `private/` key are refused, never redirected to the public bucket. Create the bucket (no public URL, no custom domain) and set the variable before SPEC-017 ships.

Observability (ARCHITECTURE §11)

- Logs are JSON lines on stdout from nestjs-pino behind the NestJS `Logger` (AR-45); `LOG_LEVEL` sets the level (default `info`). Every line carries a `correlationId`: the request's id (an incoming `x-request-id` is kept only when it matches `^[A-Za-z0-9-]{8,64}$`, otherwise a UUID; echoed in the response header) or, for a job run, its own id plus `jobName` (AR-46). A signed-in user appears only as `userHash`, an HMAC-SHA256 of the id keyed by `LOG_HASH_SECRET` (required in production; without it no user id is logged). Request lines hold method, route, status and response time; never headers, cookies, query strings or bodies, and a successful `/api/health` probe is not logged (a failing one is). Errors are logged as their class and stack frames, never their message (SC-15).
- Email verification and password reset fallback logs record only the email kind when SMTP is unavailable. No recipient data, tokens or token URLs are logged in any environment, including development (SC-15, SC-16).
- Sentry (`@sentry/nestjs`) reports 5xx faults (tagged with method and route) and failed import and scraper runs (tagged with `jobName`), scrubbed of request data, user, messages, host name and all but the runtime and trace contexts (AR-47). It is inert without `SENTRY_DSN` and always in tests. `src/instrument.ts` reads the DSN from the process environment before `.env` is loaded, so set it in the host environment.
- `GET /api/health` (public): database reachability and the outcome and age of the last Caixa import; `503` only when the database is down (AR-48). The image's `HEALTHCHECK` calls it. Field by field: `docs/runbooks/health-check.md`.

Scheduling

- Every schedule is Brasília time, whatever the server's zone (AR-25): the import of all states at 03:00, the detail-page scraper at 06:00, reminders every 15 minutes.
- With `IMPORT_ON_START_UP=true`, one initial import also runs ~5s after startup.
- Every run of the import and the details scraper is recorded in `jobexecutions` with `status` `SUCCESS` or `FAILED` (and a stable `errorCode`, never a message). A failed run does not count as "ran recently", so the next scheduled run retries (AR-03).

Notes

- CSV layout from Caixa can vary; the parser is resilient to common Portuguese headers and keeps the full `raw` row for reference.
- The download step tries GET with `?UF=<state>&Cidade=Todos`, then falls back to POST form if needed.
